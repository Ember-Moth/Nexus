# 计量与账务

首期运营币种为 USD。账户、支付和运营接口分别见[定价与预付费账户](billing-api.md)、[支付网关与自动入账](payments.md)和[查询与运营](operations.md)。

首期采用预付费余额扣费，人工登记与支付网关确认后的自动入账共用资金账本。定价由上游成本表、统一售价表、客户折扣规则组成，输入、缓存、补全等按 Token 用量计费。组织是结算和折扣主体，项目、服务账号和 Key 用于费用归属。正常调用自动完成近实时结算，不需要人工逐笔确认消费。

上述金融状态全部由 billing 模块拥有，定价、支付、计量、预算、钱包和结算是其内部子域。资金写入通过模块作用域的 Unit of Work 执行；HTTP、Worker 壳和其他模块不直接更新账表。组织创建与账户准备通过幂等事件衔接，账户未准备好时拒绝收费调用。

## 金额和账户不变量

- 金额使用 PostgreSQL `NUMERIC(28,12)`，Python 使用 Decimal，接口使用十进制字符串；不使用二进制浮点数保存或计算金额。
- 首期每个部署只启用一种运营币种。账户、价格、入账、消费和调整均携带币种，币种不一致直接拒绝，不进行隐式换汇。
- 价格单位只支持 `1`、`1000`、`1000000` 个计量单位；计算保留足够精度，最终单笔客户费用统一按 `ROUND_HALF_UP` 保留 12 位小数。
- 用于预留的费用上限向上舍入到 12 位小数，避免预留小于同一上限的最终计费金额。展示精度不改变账本精度。
- 金额与单价必须有限，拒绝 NaN、Infinity、越界和不允许的负数。

`numeric` 提供精确十进制存储，具体精度和舍入规则是本项目的业务约定。[PostgreSQL 数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)

设已记账余额为 `B`，未结清资金预留为 `H`，可用余额为 `A`：

```text
B = 所有已过账资金流水的有符号金额之和
H = 所有 held 状态预留金额之和
A = B - H
B >= H >= 0
```

首期不允许透支。缓存和汇总表不能绕过这些不变量。账户行保存余额投影和预留总额，必须能与流水及预留明细重新核对。

资金账本是产品内部的预付费账户流水，不替代公司的完整会计总账。上游成本不会再次扣减客户钱包。

## 人工登记入账

1. 财务人员创建登记草稿，填写组织、金额、币种、收款渠道、外部流水参考号、到账时间和依据说明。
2. 财务人员确认款项已在外部到账，执行过账命令。登记时间由服务器生成，到账时间保留为业务事实。
3. 在同一个事务中检查权限、幂等键、外部流水唯一性，锁定账户，追加 `funding_credit` 流水，增加余额，标记登记已过账并记录审计。
4. 请求重复提交时返回原结果，不增加第二次余额。相同幂等键对应不同参数时拒绝。

外部流水参考号在稳定的收款命名空间内唯一，防止同一笔收款给不同组织重复入账。线下收款命名空间对应真实收款账户；支付网关命名空间对应网关类型、稳定商户账户与环境，不随配置 ID 或密钥轮换改变。首期一笔收款对应一个组织，不实现收款拆分。

草稿可取消；已过账记录不能编辑金额或删除。错误入账通过引用原流水的反向调整修正，调整要有原因和操作人。反向扣减不能占用在途请求已经预留的资金；可用余额不足时进入人工处理，不制造负余额。

## 支付确认后的自动入账

支付回调必须验签；回调触发或补偿任务触发的服务端查单核实订单后，由系统执行身份生成 gateway 来源的入账登记，调用与人工登记相同的账务过账原语。即使回调漏发，也能凭可信查单结果恢复入账。订单已入账状态、入账登记、余额、唯一 `funding_credit` 流水和审计在同一个 PostgreSQL 事务中提交。

充值金额不应用客户消费折扣；首期已核实的付款金额与钱包入账金额一致，支付手续费另记。客户端支付成功页面不能作为资金依据，未知或尚在处理中的支付不能提前增加余额。

回调、主动查单和人工补单共享订单、实际收款与流水的唯一性约束。网关收款的人工补录必须关联原订单及同一交易命名空间，不得通过自由填写另一个人工来源重复入账。完整契约见[支付网关与自动入账](payments.md)。

## 成本表与售价表

成本表按上游部署、模型、计量维度和价格单位保存采购价格；售价表按公开模型、计量维度和价格单位保存统一销售价格。两者独立维护，没有隐式的“成本乘倍率”关系。上游成本变化不会自动改写客户售价。

客户费用依据统一售价乘以该企业客户的折扣系数计算。首期采用组织级统一折扣，不叠加多个折扣、不在成员或 Key 上重复折扣。8 折存储为 `0.800000`，默认无折扣为 `1.000000`，系数范围为 `0 < factor <= 1`，使用 `NUMERIC(7,6)`。

无自定义折扣的客户明确引用一条不可变的默认折扣版本，而不是把缺失值解释成零。后续如果增加模型或计费项折扣，必须另外定义明确的覆盖优先级，不能改变旧请求的解释方式。

售价版本和折扣版本在请求授权成功时由服务器共同选择并锁定；成本版本在每次上游尝试开始时锁定。客户端和网关不能指定任意历史低价或折扣进行结算。途中调价或修改折扣不影响已授权请求。

所有已发布版本不可修改，停用也不删除历史引用。费用明细保存基础售价、折扣系数、折后计算结果和成本来源，能说明客户为什么被收取该金额。折后售价低于成本时可以产生运营提示，但不能擅自提高已授权的客户费用。

同一适用范围和计价维度的生效时间区间不允许重叠。若无有效销售价，则拒绝新预留；若候选上游无有效成本价，则不能开始该尝试。不能把未知单价默认为零。

版本使用唯一的生效起点，截止时间由同作用域下一已发布版本的生效起点派生，不为发布新价格而修改旧版本。首期不允许追溯生效，恢复旧价格或恢复无折扣时都发布新版本。已锁定版本的历史请求不重新匹配生效时间。

## 用量归一化

原始证据仅保存上游返回的用量字段、上游请求标识和有限元数据，不保存提示词或生成正文。归一化由带版本的规则执行，最终费用由控制平面计算。

首期支持可验证的 Token 类计量。示例维度如下，模型只启用实际支持的维度：

| 维度 | 含义 |
| --- | --- |
| `input_uncached_tokens` | 不与缓存维度重叠的普通输入 |
| `input_cache_read_tokens` | 缓存读取输入 |
| `input_cache_write_5m_tokens` | 按短期缓存写入规则计价的输入 |
| `input_cache_write_1h_tokens` | 按长期缓存写入规则计价的输入 |
| `output_tokens` | 计价输出，包括归一化规则规定已包含的推理用量 |

这些是 Nexus 的内部维度，并不假设所有上游都以相同方式报告。上游报告的输入总数可能已经包含缓存，推理 Token 也可能是输出 Token 的子集，必须由具体归一化规则拆解，不能直接把所有字段相加。

未知维度、无法判断的缓存类别、负数、异常总数或缺失必要字段进入待核对状态。每条规范化记录保存归一化规则版本及原始事件引用。图片、音频、视频、搜索工具等计费维度在有对应规则和价格前不开放销售。

```text
客户原始费用 = Σ(互不重复的计量数量 × 基础售价 × 客户折扣 ÷ 价格单位数量)
单次尝试成本 = Σ(互不重复的计量数量 × 对应上游成本价 ÷ 价格单位数量)
客户最终费用 = 按规定精度对单次请求的客户原始费用总和舍入
请求毛利 = 客户最终费用 - 该请求全部上游尝试的已确认成本
```

费用明细保存原始数量、基础单价、折扣、价格单位与未舍入金额，最终请求费用只舍入一次。不能先舍入折后单价或将每个很小的组件舍入为零再相加。存在待核对成本时，毛利显示为暂估并注明未完成核对。

以下是算例，不是真实销售报价：

```text
普通输入 800 × 2 / 1000000 = 0.0016
缓存读取 200 × 0.5 / 1000000 = 0.0001
输出     100 × 8 / 1000000 = 0.0008
原价合计                     0.002500000000
客户 8 折后的实际费用         0.002000000000
```

## 请求授权与资金预留

首期采用逐请求预留，不使用网关本地余额作为授权依据。

1. 网关完成本地协议校验，确定公开模型、输入计量上界、输出上限和配置版本。
2. 调用 `gateway_v1.reserve_request`。数据库依据网关身份重新校验组织、项目、服务账号、Key 的有效性及模型权限，选择当前售价、客户折扣和计费策略版本。
3. 校验计量上界是否满足模型和协议约束，按所有可能计费维度及折扣计算最大销售费用 `R`。无可靠上界的模型或请求不进入首期收费范围。
4. 锁定账户及适用的预算期间，确认 `A >= R` 且各级金额预算剩余足够；创建请求与预留，增加账户和预算的预留总额。
5. 提交成功后返回请求授权结果、售价与折扣版本和预留金额。未收到明确确认时以原请求 ID 查询或重试，不能直接请求上游。

网关是受信执行组件，负责按授权上界限制实际请求；数据库不接收正文，也不能凭空验证正文的 Token 数。上界规则必须通过未来协议适配器的测试，不能用随意的估算比例宣称严格不超额。

只持有数据库锁完成短事务，绝不能在等待上游期间锁住账户行。默认可使用 Read Committed 配合明确的行锁、条件更新和唯一约束，不依赖普通查询结果完成并发扣款。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)

## 上游尝试和结果

每个客户请求有一个 `request_id`，内部重试使用不同 `attempt_id`。开始每次上游尝试前，先持久化尝试意图并锁定成本价。记录提交与上游执行之间不存在分布式事务，因此不能保证上游恰好执行一次。

首期计费策略 `customer_usage_v1` 采用以下规则：

| 结果 | 客户费用 | 上游成本 |
| --- | --- | --- |
| 请求在本地被拒绝，未开始任何尝试 | 不收费，取消已有预留 | 无 |
| 成功，具有可信最终用量 | 对最终交付尝试的用量收费 | 各尝试分别记录 |
| 客户主动取消，已有可信实际用量 | 按实际用量收费，不因断开自动全免 | 按可确认用量记录 |
| 上游失败，未完成服务，包括上游引发的流式中断 | 不向客户收费 | 仍记录可确认成本 |
| 结果或应收费的用量未知 | 保留预留，进入核对 | 独立进入成本核对 |

销售策略是首期设计选择，需在对客服务约定中明确。失败重试的额外成本由平台承担，不对客户重复收取一笔完整请求费用。流式响应开始后不得自动切换另一个响应并拼接给客户。

成本尚未核对不一定阻塞客户结算：只要客户应收费用的事实完整，即可结清客户预留，上游成本继续保留待核对状态。

## 幂等结算

Worker 只有在请求结束事实与必要用量齐全后才进行结算。在同一事务中：

1. 按固定顺序锁定账户、请求预留和相关预算期间，确认该请求尚未结算。
2. 用已锁定的售价、客户折扣和归一化规则计算客户费用 `C`。
3. 若 `0 <= C <= R`，记录费用及明细，追加唯一的 `usage_debit` 流水，执行 `B := B - C`、`H := H - R`。
4. 将预算预留转为实际消费，结清预留，更新客户结算状态和处理任务状态。
5. 提交事务。重试时返回已有结算结果，不再次改变余额。

`C = 0` 时仍记录零费用结算结果并释放预留，但无需生成无意义的零金额资金流水。

如果 `C > R`，说明上界、适配或配置存在问题。首期不自动透支、不截断用量，也不把费用偷偷改成 `R`；保留证据与预留，阻止受影响账户继续扩大敞口，进入核对。经人工确认、补充资金或明确减免后，通过有审计的命令完成结算。

## 自动化与近实时扣费

正常处理路径为：请求前预留资金，可信最终用量和结束事实提交收件箱，Worker 立即进入处理，完成计算、扣费和释放剩余预留。客户查询显示已记账余额、在途预留和可用余额，三者分别返回。

初始 Worker 空闲轮询间隔为 500 ms，队列非空时持续消费，允许小批量认领任务。可以增加提交后的通知减少等待，但通知只作唤醒，丢失时由轮询恢复，不能因通知失败丢弃已经提交的用量。

缺少前置事实的请求进入等待状态，新事件到达并完成归一化后立即重新判断是否可结算。不能把正常的乱序消息处理成长期指数退避，导致事实已经齐全仍等待很久；指数退避用于真正的暂时性执行故障。

首期性能验收目标为：在约定负载、依赖健康且结算所需事件齐全的条件下，从最后一个必要事件持久化到扣费事务提交，p95 不超过 2 秒、p99 不超过 5 秒。该数字是待实测验证的目标，不是已达到的性能或对外 SLA。

流式请求进行中已经占用预留，实时可用余额不会把这些资金再次放行。首期不对每个 Token 单独提交数据库事务，也不把部分输出的估算费用记为最终账单。最终用量到达后尽快结算；未来若需要长请求分段结算，应增加可去重的累计用量序列和差额结算契约。

迟到或缺失用量、未知结果和规则错误进入异常核对，不能为了满足秒级指标跳过账务验证。监控分别记录事件接收延迟、结算延迟和异常数量，不能把异常请求从所有可见统计中隐藏。

## 超时和状态机

```text
请求：reserved -> running -> awaiting_usage -> settled
                    |              |
                    +-----------> review
      reserved -> canceled（已确认没有开始任何上游尝试）

预留：held -> captured（费用已确认并完成结算）
      held -> released（已确认不收费）
```

到期是核对信号，不是扣费或释放资金的依据。超时预留仍为 `held`，附带 `review_required` 状态；不能用 Redis TTL 或数据库定时任务将其直接释放。

网关未开始上游尝试时，可以取消请求并释放预留。只要存在已持久化的尝试意图，就可能已经发生上游调用，需要结束事实或人工核对。迟到事件仍需被接收和去重，已结算结果的修正通过调整流程完成。

## 金额预算

组织、项目、Key 可以设置固定周期金额预算，全部适用预算都必须通过。周期使用明确的 UTC 边界，首期只实现固定日或月周期。

每次预留记录命中的预算期间，跨日或跨月完成的请求仍结算到授权时的期间，不迁移到新的期间。使用 `spent + reserved` 判断剩余额度，避免只统计已结算消费导致并发超额。

退款型消费调整同时修正原消费归属期间的净支出；人工或支付充值均不增加预算，也不改变已消费金额。过往期间的修正不改变当前期间限额。RPM、TPM 和并发控制独立在 Redis 执行，见[通信协议](plane-protocol.md)。

## 调整与对账

原始入账、用量事件、售价与成本版本、折扣版本和已过账流水不可覆盖。费用纠错产生引用原记录的调整，保留原因、依据和操作者。退款及反向调整总额不能超过可调整金额，规则通过锁定原记录与唯一键执行。

人工补充缺失用量时记录单独的核对证据与规则版本，不篡改网关原始消息。客户结算与上游成本修正各有记录，不共用一个“金额”字段。

定期核对以下关系，发现差异即记录并告警，不自动以缓存覆盖账本：

- 账户余额与资金流水总和。
- 支付订单、外部收款确认、人工或自动入账记录与唯一资金流水。
- 账户预留总额与未结清预留明细。
- 预算累计值与预算预留、消费、调整明细。
- 每个客户请求的结算结果、唯一扣费和调整链。
- 收件箱、尝试记录、请求结束事实与未处理异常。
- 已确认上游成本与人工导入或登记的上游账单依据。

首期上游对账以查询和导出支持人工核对，不自动读取厂商账单。期间报表同时提供发生时间与记账时间，迟到用量和调整以清晰的独立记录体现。
