# 控制平面验收

## 复现

在安装 Python 3.14、PostgreSQL 16 或更新版本及 Redis 的主机上运行。PostgreSQL 工具需要包含与服务端主版本匹配的 `pg_basebackup` 和 `pg_verifybackup`。测试会建立临时集群并给模拟网关创建独立登录角色，结束时清理测试实例。

```sh
uv sync --locked
uv run pytest -q -m 'not integration'
uv run python scripts/run_integration.py -q -s --capacity
```

只复测容量可在最后一条命令追加 `-m 'integration and capacity'`。日常集成测试省略 `--capacity`，保留升级、备份恢复、依赖中断、积压接管和并发状态机用例。容量测试打印所有已提交请求的统计并断言门槛，失败、超时、缺少扣费、重复扣费或待核对都会使测试失败。

## 本机负载与结果

2026-11-13，Apple M5，10 个逻辑核心，16 GiB，共享主机运行 Python 3.14.7、PostgreSQL 17.11 和 Redis 8.10.3。PostgreSQL 使用 100 个最大连接、128 MiB shared buffers，启用 fsync 和同步提交。Redis 使用 noeviction，未设置 maxmemory。API 和独立 Worker 各使用 5 个数据库池连接，overflow 为 0。4 个模拟节点分别使用独立登录和 1 个 PostgreSQL 连接。管理请求通过 ASGI 驱动，网关、Worker 和数据库通过本机 TCP 通信。

每次请求产生 1 次上游模拟尝试、1 条尝试完成事件和 1 条请求关闭事件，JSONB 转文本后每条为 421–530 字节。结算延迟取原始收件箱最后一条必要事件的**提交**到对应消费流水的**提交**，通过测试实例的 `pg_xact_commit_timestamp(xmin)` 读取。正常目标为 p95 ≤ 2 秒、p99 ≤ 5 秒。

| 场景 | 输入负载 | p95 | p99 | 错误 / 超时 / 待核对 / 未完成 | 漏扣或重复扣费 |
| --- | --- | ---: | ---: | --- | ---: |
| 稳态 | 30 秒，240 次，8.03 请求/秒，两家企业按 3∶1 分配 | 0.492 秒 | 0.509 秒 | 0 / 0 / 0 / 0 | 0 |
| 热点突发 | 单一企业，32 次，最多 16 路并发，0.042 秒内写完输入 | 0.582 秒 | 0.587 秒 | 0 / 0 / 0 / 0 | 0 |

每 50 毫秒采样一次，稳态 ready 队列和未释放预留的峰值均为 5，锁等待会话最多 1 个。突发两项峰值均为 32，采样点上的锁等待会话为 0。Worker 累计取得 1853 次连接，耗时 1.993 秒，平均 1.08 毫秒，包含连接取得和存活探测。突发提交速率只描述这一小批的写入时间。两家企业最终余额为 4676 和 4880 USD，预留均归零，按账本重新核对一致。

## 多节点与热点企业压测

在提交 `839222e` 的控制平面上，用同一台 Apple M5、PostgreSQL 17.11 和 Redis 8.10.3 测量网关到数据库的提交延迟。所有流量经过现有 Python 网关模拟器、真实 Redis 租约、网关 SQL 函数和一个独立 Worker。复现命令如下。

```sh
uv run python scripts/run_integration.py -q -s --capacity tests/integration/test_gateway_load.py
```

64 个节点各持有独立 PostgreSQL 登录和一个连接，配置预先加载。稳态每组启用 8 或 64 个节点，每个节点同时最多处理一个请求，目标 50 请求/秒，持续 30 秒，每组 1,500 次。突发由 64 个节点同时起跑，每个节点连续发送 8 个请求。8 家企业各有独立钱包和月预算，均摊组对各企业等额分配请求后洗牌，热点组约 90% 流量集中到同一家。每个请求含一次模拟上游尝试、两条用量事件，结算 2 USD。Worker 持续运行，每组结清后再开始下一组。业务链路测试期间不发布新配置、不模拟外网延迟。

预留和用量写入的 p99 采用节点单调时钟，从调用 `reserve_request` 或 `append_usage_event` 到收到 PostgreSQL 事务提交确认；用量列合并尝试完成与请求关闭两种事件。Redis 操作、生成事件和等待发起请求的时间单独于此口径。测试输出同时提供两种事件各自的 p99、发起请求的调度延迟和约 50 ms 间隔采样的 ready 队列及锁等待峰值。尾部积压按该组最后一条用量事件提交时尚未提交 done 的请求数统计，清空时间以 PostgreSQL 提交时间从该事件算至最后一个任务提交 done。

每个场景测三次，以下为逐轮观测值的最小至最大范围。首轮使用独立临时实例，随后另起实例做两遍，第二遍反转场景顺序。突发请求率只覆盖输入窗口。

| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 稳态 | 8 | 均摊 | 50.0 | 5.0–94.7 | 0.74–32.59 | 12–471 | 0.061–3.271 | 0.506–9.485 |
| 稳态 | 8 | 90% 热点 | 50.0 | 8.3–189.5 | 0.80–17.18 | 8–71 | 0.261–1.184 | 0.519–8.362 |
| 稳态 | 64 | 均摊 | 50.0 | 4.6–5.2 | 0.79–0.85 | 18–21 | 0.221–0.271 | 0.505–0.507 |
| 稳态 | 64 | 90% 热点 | 50.0 | 7.0–246.1 | 0.78–24.33 | 3–46 | 0.210–0.500 | 0.895–9.552 |
| 突发 | 64 | 均摊 | 1232.0–1659.5 | 36.0–46.6 | 6.08–11.17 | 511–512 | 2.528–2.647 | 2.509–2.626 |
| 突发 | 64 | 90% 热点 | 905.9–1024.5 | 129.1–171.2 | 1.05–1.22 | 487–508 | 2.354–2.556 | 2.336–2.536 |

合计 21,072 个请求、42,144 条用量事件。提交错误、超时、未完成、待核对、漏扣和重复扣费均为 0。每个清空检查点，组内每个请求均有两条事件、一条 2 USD 的消费流水；每次测试结束时，八个企业的钱包余额均等于流水净额，预算支出与扣费总额一致，钱包和预算预留均为零。

64 节点热点突发时，采样到 60–62 个网关数据库会话同时等锁，均摊突发为 20–23 个。预留和开始尝试都要锁定企业账户行。热点组的 512 个请求用了 0.500–0.565 秒完成输入，均摊组为 0.309–0.416 秒，因此两组用量写入的瞬时到达率不同。最后一笔用量提交后，单 Worker 在 2.354–2.647 秒内完成剩余任务。该实测覆盖本机、单次突发和预加载配置，不涵盖跨地域网络或多批连续突发。

12 组稳态测量中有 3 组结算 p99 超过 5 秒，最慢为 9.552 秒；其中 64 节点热点组逐轮为 1.482、9.552、0.895 秒。采样记录了锁等待会话数量，未分解锁等待、进程调度与提交 I/O 各自占用的时间。单轮异常或当前短时突发请求率均不足以确定稳定容量上限。

## 准入与结算优化复测

迁移到 `0012_gateway_admission` 并使用配套 Worker 与网关模拟器，复用上节压测命令、资金、预算、节点数、请求率和租户分布。基线为上节三轮记录，优化后在新隔离实例中按正序、反序各跑一轮。各格按“基线 → 优化后”列出逐轮范围。

| 场景 | 活跃节点 | 企业流量 | 预留 p99（ms） | 用量写入 p99（ms） | 清空（s） | 结算 p99（s） |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 稳态 | 8 | 90% 热点 | 8.3–189.5 → 6.0–6.1 | 0.80–17.18 → 0.48–0.53 | 0.261–1.184 → 0.053–0.070 | 0.519–8.362 → 0.193–0.207 |
| 稳态 | 8 | 均摊 | 5.0–94.7 → 4.4–4.5 | 0.74–32.59 → 0.52–0.59 | 0.061–3.271 → 0.005–0.100 | 0.506–9.485 → 0.107–0.108 |
| 稳态 | 64 | 90% 热点 | 7.0–246.1 → 5.7–7.4 | 0.78–24.33 → 0.68–1.42 | 0.210–0.500 → 0.041–0.069 | 0.895–9.552 → 0.166–0.216 |
| 稳态 | 64 | 均摊 | 4.6–5.2 → 4.0–79.6 | 0.79–0.85 → 0.51–7.29 | 0.221–0.271 → 0.008–0.011 | 0.505–0.507 → 0.107–3.723 |
| 突发 | 64 | 90% 热点 | 129.1–171.2 → 52.2–72.8 | 1.05–1.22 → 1.20–2.34 | 2.354–2.556 → 1.313–1.514 | 2.336–2.536 → 1.299–1.494 |
| 突发 | 64 | 均摊 | 36.0–46.6 → 12.9–15.2 | 6.08–11.17 → 5.33–6.64 | 2.528–2.647 → 1.749–1.760 | 2.509–2.626 → 1.730–1.746 |

本轮 14,048 个请求和 28,096 条用量事件全部提交成功，无超时、待核对、遗漏或重复扣费。八家企业的余额、预留、预算和流水一致。稳态 8 组中，0 组超过 5 秒的结算 p99 目标。

热点突发的输入窗口从 0.500–0.565 秒变为 0.556–0.825 秒，输入速率从 906–1,025 变为 621–920 请求/秒。按企业排队可以减少预留尾延迟，但会使上游尝试也等待，且让 Worker 在输入期间有更多时间处理用量。热点整批请求从首次发起到最后任务提交约为 2.07–2.14 秒（用输入耗时加尾部清空时间近似），基线约为 2.92–3.06 秒。64 节点均摊稳态有一次预留 p99 达到 79.6 ms，同轮的发起调度延迟 p99 为 16.8 ms；目前没有足够数据定位这次抖动。

在隔离库预置完整用量、排除节点流量后，对 100 笔含一次尝试和一个预算的结算计数，单笔 SQL 从 32 条减至 22 条，平均耗时从 4.82 ms 降至 3.43 ms。同一账户含 120 笔历史请求时，对账从 141 条 SQL 减至 21 条。Worker 复用当前事务中已锁定的账户、请求、尝试和冻结价格，批量核对预算明细，并批量写入报表投影。正常空闲时结算轮询间隔由 500 ms 改为 100 ms，相应增加空闲队列查询；故障重试仍使用原间隔。

网关预留与登记尝试在数据库内按企业排队。预算期间的占用和上限检查一次完成，任一预算超限会回滚所有占用。节点等待单语句事务的提交确认，开始尝试时对钱包状态持共享锁。并发冻结、预算总额正确但单笔占用错误、已提交事件丢失响应与重放均有集成测试覆盖。

## 支付确认到入账

在本地 HTTP 模拟支付渠道创建 24 笔每笔 10 USD 的订单，再持续发送已签名的收款通知。独立 Worker 查单并过账。24 笔均入账，账户余额 240 USD，无待核对事项。用于入账的服务端确认观察与对应资金流水在同一事务中提交，两个提交时间之差为 0。从通知在数据库登记到资金流水提交的 p95 为 0.484 秒，包含 Worker 调度和查单时间。

## 故障与恢复

| 演练 | 判定依据 |
| --- | --- |
| Worker 强制退出 | 停止后提交 16 份完整用量，32 USD 仍被预留。积压达到演练阈值后，新请求被拒绝，已有授权仍可重放。启动新 Worker 后 0.466 秒内完成 16 次扣费并恢复准入 |
| PostgreSQL 停止 | API 就绪检查返回 503，网关无法建立新预留。服务恢复后原预留和尝试仍可查询，补交事实只产生一条扣费流水 |
| Redis 停止并以空库重启 | 新准入失败，PostgreSQL 仍持有原预留。旧执行租约失效，网关可以从 PostgreSQL 取回快照，发布器重建 Redis 当前版本。带限流策略的恢复窗口另由租约与代次测试验证 |
| 取消或关闭请求与新增尝试竞争 | 两条独立连接使用同一节点身份并发提交，只允许一种合法结果，最终账户占用和扣费与胜出的操作一致 |
| 旧网关在途升级 | 在 0008 创建预留并登记尝试，原网关保持连接，迁移到当前版本后提交用量。Worker 正常结算，已有请求可重建报表投影 |
| 支付与消费重放 | 集成测试覆盖事务回滚、提交后响应丢失、乱序事件、支付租约接管及重复入账。密钥轮换、角色隔离和敏感信息脱敏使用同一套真实存储测试 |

## 物理备份恢复

测试先创建一笔人工充值和一笔已核实的模拟支付，结清一个请求，并保留另一个事实齐全、待结算的请求。用 `pg_basebackup -X stream` 复制整个测试集群，并用 `pg_verifybackup` 校验清单。备份完成后源库继续处理一笔新请求，用于确认恢复点边界。

将备份启动在独立端口并连接新的 Redis 实例。从测试部署配置另行提供数据库登录密码、应用加密密钥与集群私钥。恢复后验证节点权限、重新发布和解密上游凭据，重放支付通知，再启动 Worker。恢复库在补结前余额为 108 USD、占用 2 USD，补结后为 106 USD、占用 0。支付收据仍为 1 条，消费流水为 2 条，对账一致。备份后的新请求只存在于源库。

本次备份和清单校验耗时 0.433 秒；从启动恢复实例到核清账户耗时 11.419 秒。该演练覆盖单机物理快照及其自带 WAL。生产的持续 WAL 归档、指定时间点恢复、跨机切换、密钥托管以及 RPO/RTO 需在部署环境验收。Rust 网关、真实上游计量和真实商户收款也需在对应环境验收。
