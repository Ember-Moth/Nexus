# 控制平面验收

## 复现

在安装 Python 3.14、PostgreSQL 16 或更新版本及 Redis 的主机上运行。PostgreSQL 工具需要包含与服务端主版本匹配的 `pg_basebackup` 和 `pg_verifybackup`。测试会建立临时集群并给模拟网关创建独立登录角色，结束时清理测试实例。

```sh
uv sync --locked
uv run pytest -q -m 'not integration'
uv run python scripts/run_integration.py -q -s --capacity
```

只复测容量可在最后一条命令追加 `-m 'integration and capacity'`。日常集成测试省略 `--capacity`，保留升级、备份恢复、依赖中断、积压接管和并发状态机用例。容量测试打印所有已提交请求的统计并断言门槛，失败、超时、缺少扣费、重复扣费或待核对都会使测试失败。

## 本机负载与结果

2026-11-13，Apple M5，10 个逻辑核心，16 GiB，共享主机运行 Python 3.14.7、PostgreSQL 17.11 和 Redis 8.10.3。PostgreSQL 使用 100 个最大连接、128 MiB shared buffers，启用 fsync 和同步提交。Redis 使用 noeviction，未设置 maxmemory。API 和独立 Worker 各使用 5 个数据库池连接，overflow 为 0。4 个模拟节点分别使用独立登录和 1 个 PostgreSQL 连接。管理请求通过 ASGI 驱动，网关、Worker 和数据库通过本机 TCP 通信。

每次请求产生 1 次上游模拟尝试、1 条尝试完成事件和 1 条请求关闭事件，JSONB 转文本后每条为 421–530 字节。结算延迟取原始收件箱最后一条必要事件的**提交**到对应消费流水的**提交**，通过测试实例的 `pg_xact_commit_timestamp(xmin)` 读取。正常目标为 p95 ≤ 2 秒、p99 ≤ 5 秒。

| 场景 | 输入负载 | p95 | p99 | 错误 / 超时 / 待核对 / 未完成 | 漏扣或重复扣费 |
| --- | --- | ---: | ---: | --- | ---: |
| 稳态 | 30 秒，240 次，8.03 请求/秒，两家企业按 3∶1 分配 | 0.492 秒 | 0.509 秒 | 0 / 0 / 0 / 0 | 0 |
| 热点突发 | 单一企业，32 次，最多 16 路并发，0.042 秒内写完输入 | 0.582 秒 | 0.587 秒 | 0 / 0 / 0 / 0 | 0 |

每 50 毫秒采样一次，稳态 ready 队列和未释放预留的峰值均为 5，锁等待会话最多 1 个。突发两项峰值均为 32，采样点上的锁等待会话为 0。Worker 累计取得 1853 次连接，耗时 1.993 秒，平均 1.08 毫秒，包含连接取得和存活探测。突发提交速率只描述这一小批的写入时间。两家企业最终余额为 4676 和 4880 USD，预留均归零，按账本重新核对一致。

## 支付确认到入账

在本地 HTTP 模拟支付渠道创建 24 笔每笔 10 USD 的订单，再持续发送已签名的收款通知。独立 Worker 查单并过账。24 笔均入账，账户余额 240 USD，无待核对事项。用于入账的服务端确认观察与对应资金流水在同一事务中提交，两个提交时间之差为 0。从通知在数据库登记到资金流水提交的 p95 为 0.484 秒，包含 Worker 调度和查单时间。

## 故障与恢复

| 演练 | 判定依据 |
| --- | --- |
| Worker 强制退出 | 停止后提交 16 份完整用量，32 USD 仍被预留。积压达到演练阈值后，新请求被拒绝，已有授权仍可重放。启动新 Worker 后 0.466 秒内完成 16 次扣费并恢复准入 |
| PostgreSQL 停止 | API 就绪检查返回 503，网关无法建立新预留。服务恢复后原预留和尝试仍可查询，补交事实只产生一条扣费流水 |
| Redis 停止并以空库重启 | 新准入失败，PostgreSQL 仍持有原预留。旧执行租约失效，网关可以从 PostgreSQL 取回快照，发布器重建 Redis 当前版本。带限流策略的恢复窗口另由租约与代次测试验证 |
| 取消或关闭请求与新增尝试竞争 | 两条独立连接使用同一节点身份并发提交，只允许一种合法结果，最终账户占用和扣费与胜出的操作一致 |
| 旧网关在途升级 | 在 0008 创建预留并登记尝试，原网关保持连接，迁移到当前版本后提交用量。Worker 正常结算，已有请求可重建报表投影 |
| 支付与消费重放 | 集成测试覆盖事务回滚、提交后响应丢失、乱序事件、支付租约接管及重复入账。密钥轮换、角色隔离和敏感信息脱敏使用同一套真实存储测试 |

## 物理备份恢复

测试先创建一笔人工充值和一笔已核实的模拟支付，结清一个请求，并保留另一个事实齐全、待结算的请求。用 `pg_basebackup -X stream` 复制整个测试集群，并用 `pg_verifybackup` 校验清单。备份完成后源库继续处理一笔新请求，用于确认恢复点边界。

将备份启动在独立端口并连接新的 Redis 实例。从测试部署配置另行提供数据库登录密码、应用加密密钥与集群私钥。恢复后验证节点权限、重新发布和解密上游凭据，重放支付通知，再启动 Worker。恢复库在补结前余额为 108 USD、占用 2 USD，补结后为 106 USD、占用 0。支付收据仍为 1 条，消费流水为 2 条，对账一致。备份后的新请求只存在于源库。

本次备份和清单校验耗时 0.433 秒；从启动恢复实例到核清账户耗时 11.419 秒。该演练覆盖单机物理快照及其自带 WAL。生产的持续 WAL 归档、指定时间点恢复、跨机切换、密钥托管以及 RPO/RTO 需在部署环境验收。Rust 网关、真实上游计量和真实商户收款也需在对应环境验收。
