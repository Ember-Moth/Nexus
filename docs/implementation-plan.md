控制平面设计基线 v1.0 已于 2026-11-08 定稿，M0 与 M1 已完成。后续按可验证的业务流程逐步实现，支付采用通用适配接口；Rust 网关、自建管理网站与收银页面另行安排。

## M1 工程基线

初始化时核实并锁定受支持的 Python、FastAPI、Uvicorn、uvloop、SQLAlchemy、psycopg、Alembic 和 Redis 客户端版本。使用一致的依赖锁文件和配置校验；生产配置缺少必要密钥时拒绝启动。

分别提供 API、Worker、数据库迁移和初始管理员引导入口。迁移使用独立高权限角色，运行服务不携带迁移权限。以单一部署可运行的模块化单体起步，保持 API 与 Worker 可独立扩容。

模块骨架采用[系统架构](architecture.md)的五个数据所有权边界，参考依据记录在 [PPanel 设计参考](ppanel-reference.md)。HTTP 接口按需放在业务包的 api.py；bootstrap.py 组装真实依赖，业务服务不反向依赖启动入口。目录按 Python 用例组织，不复制 PPanel 框架模板。pricing、payments、metering、wallet 和 settlement 作为 billing 子域一起维护资金不变量。

本阶段建立必要的测试设施：真实 PostgreSQL 事务与迁移测试、Redis 原子行为测试、API 鉴权测试。不能用 SQLite 替代 PostgreSQL 验证锁、数值、函数权限和并发资金约束。

## 架构验收

- AST 检查业务代码不导入 bootstrap、其他模块只使用公开导出，持久化和 HTTP 框架不侵入业务服务；不强制统一 Facade/Deps/internal 目录。
- 模块自己的 handler 只调用所属门面；共用认证依赖仅通过 identity 的公开认证能力取得上下文。
- 组装测试验证真实业务服务与五个存储作用域的依赖，使用本地替身隔离资源，不为健康探测创建空业务服务。
- 仓储和 Unit of Work 归属单一模块；网关 SQL 桥接清单只允许公开只读能力组合和单业务模块写入。
- 跨模块事件有生产方主题常量、版本和幂等键；组织与账户准备流程可重复执行，不重复开户。
- 模块自有审计/outbox/inbox 与本域副作用一起提交；reporting 只更新投影，不改原始资金事实。
- 临时移除或替换支付厂商适配器不要求修改其他模块、账本逻辑或各回调 handler；未注册渠道明确拒绝。

M1 已落地导入边界、组装与基础存储权限检查。尚未实现的事件、支付适配器和 SQL 桥接随对应模块阶段补充检查，不因使用 Python 私有目录名就认为边界已被语言自动保证。

## 关键领域验收

| 领域 | 必须验证的行为 |
| --- | --- |
| 租户隔离 | 伪造组织 ID、跨组织外键、越权项目查询、导出和间接关联均失败 |
| 账户准备 | 组织创建事件和账户准备事件重放不重复建账户；provisioning 状态不能发起收费调用 |
| 角色 | 企业可按权限发起支付，不能改售价、折扣或直接增加余额；平台管理员未获财务角色时不能人工过账 |
| Key | 撤销生效、轮换重叠期受控、摘要可验证、响应和日志不泄露历史秘密 |
| 人工入账 | 重复请求、不同幂等键但同收款依据、跨组织复用收款均不重复入账 |
| 支付确认 | 伪造签名、前端跳转、仅授权未收款、金额或币种不符、错商户或错环境均不能入账 |
| 支付幂等 | 重复与乱序回调、主动查单、人工补单和密钥轮换后重放均不重复增余额 |
| 支付金额 | 精确转换外部金额单位，不以手续费净额给客户少入账，不对充值应用消费折扣 |
| 价格与折扣 | 无折扣为 1，8 折为 0.8；版本切换不影响在途请求；成本变化不改变售价 |
| Token 计量 | 输入与缓存不重计，输出与推理子集不重计，未知维度不默认免费 |
| 精度 | 先精确累加再舍入，折扣不提前截断，极小费用、边界数值和非法数值有确定结果 |
| 并发预留 | 余额 1、两个并发预留各 0.8，只能一个成功；预算同步受约束 |
| 结算 | 实际费用小于预留时准确扣费并释放差额；零费用释放；超上限进入核对 |
| 取消与超时 | 无尝试可取消；已开始尝试不能因 TTL 到期自动释放资金 |
| 幂等 | 重放、乱序、换 event_id 的重复事实及提交响应丢失都不会双扣 |
| 多次尝试 | 失败尝试成本独立记录，客户只按计费规则承担一次最终费用 |
| 调整 | 不改原流水，不能重复退款或冲回已经占用的资金，预算归属保持一致 |
| 权威状态 | 余额与流水、预留与明细、预算与占用可独立重建核对 |

金额算例和状态机测试应覆盖实际业务不变量，不为每个数据字段机械复制一组实现镜像测试。

## 通信与故障验收

1. 数据库角色只能调用批准的桥接操作，伪造节点和跨集群读取被拒绝。
2. 配置发布事务失败时没有半份快照；Worker 写 Redis 后崩溃，重试不会回退版本。
3. 节点错过通知、断线重连或启动于发布过程中，仍能获得完整一致快照。
4. 旧配置回滚以新 revision 发布；未知必需能力导致拒绝应用，而不是部分应用。
5. 用量事务已提交但响应丢失，重试返回原接收结果；同 ID 不同内容产生冲突。
6. 结算 Worker 在认领后、计算后、提交前或提交后崩溃，都能接管且不重复记账。
7. 请求关闭与新增尝试、请求取消与开始尝试并发时，状态机保持合法。
8. PostgreSQL、Redis、Worker 分别故障时，系统按架构文档执行拒绝、积压或核对策略。
9. Redis 清空与故障切换不能使数据库中的资金预留消失；运行限额按明确的恢复策略处理。
10. 缺少最终用量时保留异常和预留，不能仅为让测试通过而生成估算账单。
11. 支付下单响应丢失时查回原订单；回调先于下单响应、迟到成功或漏回调，都能按实际收款事实恢复。
12. 支付入账事务提交前后崩溃，订单与余额不会出现半完成状态；回调接收存储失败时不返回成功确认。
13. 支付渠道停用后仍可处理历史订单；收到外部退款、撤销或争议时保留证据并进入核对，不自动双重充值或制造负余额。
14. 支付任务创建意图已经提交后失去租约，接管者先查单；关单查询后的创建代次或状态变化导致重新核对，不能使用旧结论覆盖新交易。
15. 表单和 query 中重复的签名参数在转成单值字典前被识别；原始 body、合法生命周期通知、永久拒绝和暂时失败分别符合 NotificationStyle。
16. 支付确认、充值过账和入账事件在同一 billing 事务中提交；提交后报表投影或通知失败不会重加余额。

使用 Python 协议模拟器生成有效、重复、乱序、冲突和缺失事件，验证 PostgreSQL 接口、Redis 配置和自动结算。模拟器不是 AI 转发网关，不引入真实厂商账号或 Rust 实现。

支付侧另设通用模拟适配器，验证订单、通知、查单和原子入账。具体网关确定后再实现其官方协议适配和沙箱集成；通用层通过不代表真实收款已经可用。

## 近实时与容量验收

正常请求的结算时效目标见[计量与账务](billing.md)：必要事件齐全并持久化后，到扣费事务提交的 p95 ≤ 2 秒、p99 ≤ 5 秒。必须同时报告未完成、异常和超时请求数量，不能只展示成功样本。

测试负载需要包含以下维度，并在每次结果中记录：

- 网关模拟节点数、并发请求数、持续请求率、事件大小和每请求尝试次数。
- 企业数量与流量分布，尤其是同一企业产生大量并发的账户热点。
- API、Worker 和节点连接池配置，以及 PostgreSQL、Redis 的资源配置。
- 数据库锁等待、池等待、收件箱积压、预留数量和结算延迟。
- 稳态、短时突发、Worker 重启后的追赶速度，以及依赖故障后的恢复行为。

首先测量逐请求预留和 PostgreSQL 收件箱的真实瓶颈。只有数据证明需要时，才评估额度租约、接入服务、队列缓冲或分区；这些优化不能以放松资金不变量为默认前提。

## 生产准备

生产部署前确定运营币种、实际模型与价格、折扣、故障处理阈值、保留期、备份 RPO/RTO 和密钥引导方式。价格可用、归一化可靠、请求上界可验证，是模型开放收费的前置条件。

启用真实自动入账前，还需选定支付渠道、验证商户与回调配置、明确支付方式的确认条件、金额精度与幂等期限，并完成漏回调补偿和收款对账演练。首期只做客户发起的充值，不开启自动扣卡或自动对外退款。

完成数据库恢复演练、密钥轮换演练、最低权限检查和日志脱敏检查。升级采用可兼容旧调用方的迁移顺序，禁止把开发环境的凭据或测试入账带入生产。

人员流程需明确谁登记线下收款、谁处理支付与消费异常、如何提供依据以及何时需要复核。已核实的在线收款与正常消费自动处理，异常处理不会隐式改变客户已接受的价格和折扣。

## 数据平面后续阶段

Rust 网关另行开展设计和开发，范围包括负载均衡接入、请求鉴权执行、协议适配、连接池、流式处理、受控重试、上游取消、用量归集、全局限流执行和优雅下线。

接入前必须跑通控制平面契约测试，并使用真实上游验证 Token 归一化、取消后用量、超时结果和费用上界。仅通过模拟器不代表真实上游计费、性能或端到端可用性已经通过验收。
