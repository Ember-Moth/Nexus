# Relay 容量验收（P5）

本报告对应[开发计划](relay-development.md#阶段依赖与交付)的 P5 行和其后的“负载口径”。测量对象是 release 构建的 Rust Relay（`nexus-relay`），而不是[控制平面验收](control-plane-acceptance.md)中的 Python 网关模拟器。数据只代表下文这台共享开发机和本地 TLS 上游替身，**不能当作部署环境的容量**：没有真实网络往返、真实上游和跨地域延迟，PostgreSQL、Redis、Worker、全部 Relay、上游替身和压测客户端运行在同一台机器上，并且与其他会话的任务共享 CPU。

## 结论

- **结算目标（p95 ≤ 2 秒、p99 ≤ 5 秒）只在部分场景达到。** 达到的场景：4 个节点下 HTTP、SSE、WebSocket、故障转移的常规负载；64 个节点、90% 热点企业的稳态，在每个节点的连接池降到 2 时也能达到（p99 0.53–1.23 秒）。8 个节点 50 请求/秒时，p99 为 2.27–9.71 秒，各轮差异很大，取决于主机负载。按默认配置（每个节点 8 个连接）未达到的场景：64 个节点的稳态（热点 p99 3.30–9.15 秒，均摊 7.46–8.47 秒），以及 64 个节点同时突发 512 个请求（均摊 p99 5.49–11.0 秒；热点有 48–188 个请求返回 503）。范围中数值较大的一端多数出现在主机繁忙的轮次。
- **Relay 进程本身不是瓶颈。** 50 请求/秒时，全部 64 个 Relay 合计只用 0.1–0.17 个核；普通请求下每个进程 RSS 为 14–35 MiB。4 个节点转发 count_tokens 时可以达到每秒 3,000–4,000 个请求。100 路同时持续 30 秒的 SSE 长流、200 个空闲 WebSocket 连接和慢客户端，都没有让内存失控。
- **集群容量在这台机器上受三处限制，三处都在 Relay 之外**：
  1. **热点企业的预留串行，叠加节点连接数。** `reserve_request` 和 `start_attempt` 都要先取企业级 advisory lock。64 个节点、每节点 8 个连接时，最多有约 500 个会话排队等同一把锁。排队超过 5 秒后，节点拿不到连接池连接，第一条 SQL（`get_credential_envelope`）就失败，请求返回 503。热点企业还会占满节点的连接，连带阻塞同一节点上其他企业的请求。把连接池从 8 降到 2，512 个热点突发请求从 324–326 个成功变为全部成功；延长 `deadlock_timeout` 没有改善。
  2. **单个 Python Worker 的结算速度。** 每结算一笔约需 7–13 ms CPU，积压时清空速度约为每秒 45–140 笔。持续输入超过这个速度后，积压达到 `settlement_backlog_limit`（1,024）时，新的预留会被拒绝。实测 Messages 以每秒约 1,080 个请求输入时，约 46% 的请求返回 503。
  3. **快照规模。** 每次预留和开始尝试，都会在 SQL 里展开整个快照，并对 Key 列表做线性扫描。节点每 2–3 秒还会拉取一次完整快照。1 万个 Key 时，`reserve_request` 的 p50 从 1.5 ms 升到 13.9 ms，每个 Relay 的 RSS 升到约 96 MiB。10 万个 Key 时，单次拉取需要 0.84–1.56 秒，每个 Relay 的 RSS 达到 409 MiB，20 请求/秒的负载全部失败。这组数据只有一轮，而且运行时主机较忙。
- **资金一致性**：全部 profile 都完成了核对，67,960 个已扣费请求中，重复扣费、漏扣和金额错误都是 0。预留要么归零，要么按设计进入 review：故障转移中失败的尝试、WS 中途断线，以及被中断的慢客户端流。
- **大致容量（只代表本机和本地上游替身）**：
  - 单个 Relay 节点的 CPU 足以处理每秒上千个普通请求，实际上限由 PostgreSQL 决定。
  - 集群可以持续承受约 50 请求/秒并满足结算目标，前提是每个节点连接池 ≤ 4，并且主机不被其他任务占满。
  - 单个 Worker 的结算速度约为每秒 100 笔，这是集群的持续吞吐上限。
  - 单个企业的串行预留在连接池为 2 时可以处理每秒约 150–400 个请求，但同一时刻排队的会话数必须受到限制。
- **建议**按收益和成本排序：
  1. 按“节点数 × 连接池 ≤ PostgreSQL 核数的 2–4 倍”设置连接池，64 个节点时设为 2；
  2. 把准入 SQL 中的快照展开换成按 Key 的索引查找，并让节点只在修订变化时才拉取快照；
  3. 合并 `reserve_request` 和 `start_attempt`，并让 Worker 能够水平扩展；
  4. 给节点预先分配额度的风险较高，只适合作为最后手段。

  详见[瓶颈](#瓶颈分析)和[建议](#优化建议)。

本次运行没有修改产品代码。找到的瓶颈要么需要协议或迁移层面的改动，要么会影响资金或交付语义，都不属于“小而安全”的修复，因此只写入建议。

**后续：** 准入路径的建议（1、2、3、5、6、7）已经实现，改动前后的对比和对上文一处归因的更正（64 节点 × 8 连接突发的 503 来自 macOS 的监听队列）见[优化后](#优化后)。

## 复现

```sh
mkdir -p /tmp/nexus-p5
TMPDIR=/tmp/nexus-p5 LC_ALL=en_US.UTF-8 \
  uv run python scripts/relay_load.py --out /tmp/nexus-p5/report
```

`TMPDIR` 必须是短路径：PostgreSQL 的 Unix socket 路径不能超过 103 字节。macOS 上需要 `LC_ALL=en_US.UTF-8`，否则 PostgreSQL 会以 “postmaster became multithreaded” 退出。`--scenarios control,pools,hotwallet,http,ws,tokens,snapshot,failover` 选择场景，`--rounds` 设置轮数（默认 2），`RELAY_LOAD_PROFILES=子串,…` 只运行名称匹配的 profile，`RELAY_LOAD_WORKERS=N` 在本机启动 N 个 Worker 进程（默认 1），`RELAY_LOAD_SNAPSHOT_KEYS`、`RELAY_LOAD_SNAPSHOT_NODES` 调整快照场景。开发时可以加 `--workspace DIR --keep` 复用服务。

脚手架由以下文件组成：

| 文件 | 作用 |
| --- | --- |
| `scripts/relay_load.py` | 构建 release Relay；启动隔离的 PostgreSQL 和 Redis 并迁移；运行 `capacity` 测试；记录主机负载；把 `results.jsonl` 汇总成 `summary.md`，每个指标给出各轮的最小–最大范围 |
| `scripts/relay_upstream.py` | 本地 TLS 上游替身。同一端口提供 Responses（JSON、SSE、WebSocket）和 Messages（JSON、SSE、count_tokens），支持 HTTP/1.1 keep-alive。路径前缀 `/a/v1`、`/b/v1` 选择通道；每个通道可以通过控制端口设置首字节延迟、事件数、事件间隔、事件大小、用量和错误率（429 或 503 都使用厂商文档规定的错误信封） |
| `tests/integration/relay_load_kit.py` | Relay 进程组（每个进程使用独立的节点数据库登录）、原始 HTTP/1.1 客户端、`pg_stat_activity` 采样、进程 RSS/CPU 采样、PostgreSQL 语句耗时、账本核对 |
| `tests/integration/test_relay_load.py` | 场景。带 `integration` 和 `capacity` 标记，只有通过 `scripts/relay_load.py` 运行时才会执行 |
| `src/relay/tests/tokenizer_capacity.rs` | 本地分词估算器的离线测量（`#[ignore]`，由 `tokens` 场景调用） |

## 测量方法

**负载生成。** 客户端是同一 Python 进程中的原始 HTTP/1.1 客户端。Relay 对每个响应都关闭连接，所以每个请求都会新建 TCP 连接。稳态 profile 采用开环到达：请求按计划时间发出，不等待前一个请求完成。突发 profile 同时发出全部请求。请求按顺序轮流分配到各节点。WebSocket 使用 `websockets` 客户端。

**指标口径。**

| 指标 | 定义 |
| --- | --- |
| 输入速率 | 成功请求数 ÷（第一个请求发出 → 最后一条用量证据提交）。与 Python 基线的“实际输入请求/秒”口径相同 |
| 上游前开销 | 客户端发出请求 → 上游替身收到请求，两边都使用系统范围的 `time.monotonic`。包含 Key 鉴权、Redis 租约、`get_credential_envelope`、`reserve_request`、`start_attempt`、连接池等待和连接上游 |
| 证据提交延迟 | 上游替身写完响应（墙钟）→ 该请求最后一条用量事件提交（`pg_xact_commit_timestamp`）。包含写给客户端、等待写出回执、两次 `append_usage_event` 和连接池等待 |
| SQL 耗时 | 每个节点登录都设置了 `log_min_duration_statement=0`，从 PostgreSQL 日志解析每条 `gateway_v1.*` 在服务端的 execute 耗时。包含锁等待，不包含连接池等待和网络往返 |
| 结算 p95/p99 | 最后一条用量证据提交 → 对应 `usage_debit` 提交，与 Python 基线相同 |
| 输入结束积压、清空 | 最后一条用量证据提交时仍未结算的请求数；从该时刻到最后一个任务 `done` 的时间 |
| 锁等待、连接池 | 每 100 ms 采样一次节点登录在 `pg_stat_activity` 中的会话：`wait_event_type='Lock'` 的会话数、连接数，以及“某个节点的活跃连接数达到池上限”的采样占比（此时新的 SQL 调用必须等待连接池） |
| RSS、CPU | 每 500 ms 用 `ps` 采样一次 Relay、PostgreSQL（postmaster 及其子进程）、Redis、Worker、上游替身和客户端。CPU 以“核”为单位，等于 CPU 时间增量 ÷ 墙钟时间 |

**资金一致性。** 每个 profile 结算后都会核对：每个成功交付的请求恰好一笔 `usage_debit`，金额等于上游替身报告的用量乘以售价；没有重复扣费；不在 review 状态的请求不再持有预留；每个钱包的 `held_amount` 等于仍持有预留的请求之和；每个钱包余额等于其流水之和；每个预算期间的 `reserved` 等于其预算占用之和。进入 review 的请求会列出原因（例如 `unknown_outcome`、`missing_usage`），这也是设计中的核对路径。

**可信度。** 每个 profile 开始前，脚手架会等待其他进程的 CPU 占用降到 250%（2.5 个核）以下，最多等待 5 分钟。运行期间每 2 秒采样一次其他进程的 CPU。运行期间均值超过 250% 的 profile 会被标记为 contended，并最多重跑两次。每条记录都保存了运行前后的 `load1`、`load5`、核数，以及运行期间其他进程的 CPU 均值和峰值。下表中的范围取每轮最后一次运行的结果；如果重跑后仍然是 contended，会单独注明。

## 结果

除非另有说明，表中数值都是两轮的最小–最大范围，第二轮按相反顺序运行各 profile。标记 ⚠n 表示有 n 轮在重跑两次后仍被判为 contended，即运行期间其他进程的 CPU 均值超过 250%。各列的口径见[测量方法](#测量方法)。

Python 模拟器的每个节点只有一个连接，同一时刻只处理一个请求。突发时，它在每个节点上依次发送 8 个请求。Rust Relay 的每个节点有 8 个连接，同一时刻会把 8 个请求都送进 PostgreSQL。因此两组数据只能比较量级，不能逐格对比。

### 故障转移

### 资金一致性

全部 89 个带账本检查的 profile 记录中，共有 67,960 个请求被扣费：重复扣费、漏扣和金额错误都是 0；不在 review 状态却仍持有预留的请求为 0；钱包余额与流水、`held_amount` 与仍持有的预留、预算期间的 `reserved` 与预算占用之间，不一致都是 0；没有未完成的请求。进入 review 的请求都是预期的核对路径：

- 故障转移：每个失败尝试一个 `missing_usage`，共 2,500 个，客户只按交付的尝试扣费一次；
- WS 中途断线：64 个 `unknown_outcome`，以及 64 个 `missing_usage`；
- 慢客户端：1 个流被上游中断，`unknown_outcome` 和 `missing_usage` 各一个。

因 `settlement_backlog`、连接池超时、语句超时被拒绝的请求，要么没有预留，要么已经以 `canceled/released` 释放了预留。

## 与结算目标对照

目标是从最后一条用量证据提交到扣费提交，p95 ≤ 2 秒、p99 ≤ 5 秒。

| 场景 | 结算 p95 / p99（s） | 是否达标 |
| --- | --- | --- |
| 稳态 8 节点热点 | 0.63–2.47 / 0.79–2.66 | p99 达标；p95 在 2 轮中有 1 轮超标 |
| 稳态 8 节点均摊 | 2.14–9.61 / 2.27–9.71 | 未达标：没有被标记的那一轮 p99 为 2.27 秒，p95 为 2.14 秒，略超目标；超标严重的那一轮被标记为 contended |
| 稳态 64 节点热点（连接池 8 / 4 / 2） | 2.77–8.62 / 3.30–9.15；1.83–2.58 / 2.30–2.68；0.45–1.06 / 0.53–1.23 | 只有连接池为 2 时 p95 和 p99 都达标；连接池为 4 时 p99 达标 |
| 稳态 64 节点均摊 | 7.18–8.30 / 7.46–8.47 | 未达标 |
| 突发 64 节点均摊 / 热点（连接池 8） | 5.40–10.9 / 5.49–11.0；3.55–3.96 / 3.56–3.98，且有 503 | 未达标 |
| 突发 64 节点热点（连接池 2） | 3.28–4.49 / 3.38–4.58 | p99 达标，p95 未达标；全部成功 |
| HTTP、SSE、长流、上游延迟、慢客户端 | ≤ 0.12 / ≤ 0.12 | 达标 |
| 配置发布期间 | — / 0.30–1.93 | 达标 |
| WS 多轮、长轮、慢读 | — / 0.09–1.99 | 达标 |
| 故障转移（单轮） | — / 0.11–3.84 | p99 达标 |

在稳态下，结算延迟没有达标的原因是 Worker 的处理能力不够，Relay 本身不是原因。这些 profile 运行时，Worker 每秒只能清空 45–140 笔，与输入速率相当，一旦主机繁忙就会积压。突发 profile 的结算时间至少等于清空 500 个积压所需的时间，即 3–11 秒。达到突发场景的目标需要提高 Worker 的吞吐（建议 4）。

## 瓶颈分析

### 1. 热点企业串行，并且节点连接数没有上限

- **机制。** `gateway_v1.reserve_request` 最终调用 `billing.v1_reserve_guarded_capacity`，先执行 `pg_advisory_xact_lock(hashtextextended(org::text,398221))`，再对钱包执行 `SELECT … FOR UPDATE`。`gateway_v1.start_attempt` 调用 `billing.v1_attempt`，先取同一把 advisory lock，再对钱包执行 `FOR SHARE`。所以同一企业的每个请求要依次通过两个串行区，每个串行区都包含一次同步提交。两把锁都在事务结束时才释放，所以快照展开和 Key 扫描（见下文）虽然在取锁之前执行，也会拉长事务。
- **证据。**
  - 64 个节点、每节点 8 个连接时，热点突发采样到 459–475 个会话处于 `wait_event_type=Lock`（`advisory`），节点连接峰值 513 个。`reserve_request` 和 `start_attempt` 在服务端的 p99 都接近 8 秒的 statement_timeout（7.5–8.0 秒）。
  - 50–52% 的采样点上，至少有一个节点的 8 个连接全部处于活跃状态。失败的请求都停在第一条 SQL（`get_credential_envelope`，连接池等待超过 5 秒）或语句超时。
  - 同一负载下，连接池从 8 降到 2，锁等待峰值从约 300 降到 127，突发全部成功，`reserve_request` 的 p99 降到 0.11–0.88 秒。
  - 延长 `deadlock_timeout` 没有效果。
- **影响范围。** 热点企业会占满一个节点的全部连接。同一节点上其他企业的请求，即使它们的企业锁没有竞争，也要等待连接池。在 64 个节点、8 个连接的均摊突发中，也有 236–385 个会话在等锁。
- **单个企业的串行吞吐。** 连接池为 2 时，热点突发的输入速率为 154–431 请求/秒（其中 90% 属于热点企业）。这就是本机上单个企业在等锁会话数受控时的大致上限。

### 2. 单个 Worker 的结算吞吐

- **证据。**
  - 每个 profile 的 Worker CPU 时间除以已结算的请求数，得到每笔 7–13 ms（最小 5.8 ms，最大 16.4 ms）。
  - 大批积压时（突发后积压约 500 笔）的清空速度为 45–143 笔/秒，Python 基线为 290–390 笔/秒。
  - 50 请求/秒的稳态下，Worker 已经用掉 0.4–0.64 个核。主机繁忙、Worker 被调度到能效核上时，它跟不上输入，积压上升到 300–970 笔。
  - 以每秒约 1,080 个请求输入时，积压在 1 秒左右达到 1,024，新的预留被拒绝。
- **补测与优化。** `hotwallet` 场景后来补跑了：Worker 锁钱包行是热点预留尾延迟的主因，backlog 扫描是次要因素。原因拆分、优化和前后对比见[Worker 优化后](#worker-优化后)。

### 3. 快照规模放大每个请求的 SQL 成本

- **机制。**
  - **SQL 侧。** `reserve_with_guardrail`（`reserve_request` 的最终实现）和 `start_attempt` 都调用 `publication.v1_snapshot(rev, …)->'manifest'`。这个函数每次都会解开整个 manifest，并且执行 `encode(s.payload_bytes,'base64')`，即使调用方只需要 manifest。随后，`reserve` 还要用两次 `jsonb_array_elements` 对 `key_verifiers` 做线性扫描。所以每个请求的数据库成本随集群内的 Key 数线性增长。
  - **节点侧。** 每个节点每 2–3 秒调用一次 `get_config_snapshot`（`src/relay/src/server/mod.rs` 的维护循环），每次都拉取完整应答、解码并解析，与修订是否变化无关。
- **证据。** 1 万个 Key 时，`reserve_request` 的 p50 是无 Key 时的 9 倍，`start_attempt` 的 p50 是 10 倍，每个节点 RSS 约 96 MiB，空闲出口 22 MB/s。10 万个 Key 时，单次拉取 0.84–1.56 秒，每个节点 RSS 409 MiB，空闲出口约 160 MB/s。20 请求/秒的负载全部失败，原因是 `start_attempt` 超过 1 秒、语句超时，以及刷新失败。
- **结论。** 现有的全量快照设计只适合每个集群约 1 万个 Key 以内。

### 4. 次要发现

- **配置刷新和请求共用连接池。** 连接池被锁等待占满时，`control-plane refresh failed` 会把节点标为不健康，节点随后拒绝所有企业的请求，也会延迟应用新快照。突发和 10 万 Key 的 profile 中，每次记录到 1–34 次这样的失败。
- **慢客户端可能被判为交付未知。** 见 HTTP 一节。
- **故障转移的成本核对随流量增长。** 主部署持续返回 429 或 503 时，每个请求都会产生一个 `missing_usage` 核对事项。已修改，见[Worker 优化后](#故障转移的核对事项)。

## 优化建议

按收益和成本从高到低排列：

1. **按上表限制节点连接池，必要时在 PostgreSQL 前加连接池代理（成本低，收益高）。** 只需要改配置和文档。注意：Relay 在 `after_connect` 中执行 `SET statement_timeout`，PgBouncer 的 transaction 模式不会保留这类会话级设置，所以要么改用角色级设置，要么使用 session 模式。
2. **准入 SQL 不再展开快照（成本中等，收益高）。** 新增一个只返回所需字段的函数，例如只返回 manifest、不做 base64 的 `v1_manifest`，并在发布时把 Key 校验数据写入按 `(cluster_id, revision, key_id)` 建索引的表。`reserve_*` 和 `start_attempt` 改为按索引查找。这样每个请求的成本与 Key 数无关。需要新迁移和发布路径的配合，不改变资金语义。
3. **快照只在修订变化时拉取，并支持 Key 增量或回查（成本中等，收益高）。** 先用轻量函数（只返回修订号、sha256 和已应用修订号）或 Redis 当前指针判断是否变化，没有变化就不拉取；`get_config_snapshot` 只返回原文。Key 有两种方式：一是从快照中拆出来，按 identity 序号增量下发；二是快照中找不到时，调用按摘要查询的 `gateway_v1` 函数回查，并对未命中做负缓存和限速。这一项需要改协议和 Relay。注意：现在的周期性全量拉取同时承担 Key 撤销和集群范围失效（`snapshot_scope_expired`）的检测，改为条件拉取时必须保留这些检测的时限。
4. **提高 Worker 吞吐，并让它水平扩展（成本中等，收益高）。已完成，见[Worker 优化后](#worker-优化后)。** 先分析每笔 7–13 ms CPU 的构成：归一化、成本记录、报表投影等。然后验证多个 Worker 进程并发结算的正确性和吞吐，Worker 认领任务已经使用 `SKIP LOCKED`。还可以评估按账户批量结算：在一个事务里结算同一账户的多笔请求，减少对热点钱包行的加锁次数。
5. **合并 `reserve_request` 和 `start_attempt`（成本中等，收益中高）。** 预留时节点已经选好了部署，可以在同一个事务中登记第一次尝试。这样热点企业每个请求只经过一次串行区，少一次往返，也少一次同步提交。故障转移时的后续尝试仍然使用 `start_attempt`。要保持“预留成功但尝试登记失败”时的取消语义。
6. **配置刷新使用单独的连接（成本低，收益中）。** 维护循环从主连接池的连接参数单独建一个连接，避免请求的锁等待把节点刷成不健康、进而拒绝所有企业的请求。需要先决定：连接池耗尽时节点是否应该退出负载均衡。
7. **SSE 和 WS 按写出进展判定交付（成本低，涉及交付语义）。** 把等待终态写出的固定 30 秒改为“30 秒内没有写出进展才超时”，或者在 Relay 侧限制排队的字节数，让慢客户端的背压传到上游。这会改变“交付未知”的判定，需要按资金语义评审，本次没有修改。
8. **故障转移产生的核对事项合并处理（成本低到中）。被换掉的尝试已改为零成本确认，见[故障转移的核对事项](#故障转移的核对事项)。** 对“厂商文档已证明没有执行”的失败尝试（Declined），可以记录为零成本，或者按部署和时段汇总，避免核对队列随流量增长。
9. **给节点预先分配额度（成本高，热点收益最高，有超支风险）。** 节点一次从钱包和预算预留一块额度（例如 50 USD），之后在本地为每个请求扣减这块额度，只有补充额度时才取企业锁。评估如下：
   - **收益。** 热点企业不再按请求串行，吞吐取决于补充频率。
   - **超支风险。** 最大超支等于所有节点未用额度之和。例如 64 个节点 × 50 USD = 3,200 USD。冻结钱包、停用 Key 或预算到期时，需要立即收回所有节点的额度；节点崩溃时，额度要到租期结束才释放。
   - **预算语义的变化。** 项目和 Key 层级的预算必须分别分配额度，否则只能在本地近似检查，这会把“预留前精确拒绝”变成“在额度范围内允许超出”。
   - **账本仍按请求结算。** Worker 要把每笔用量归到对应的额度块，并处理退还。

   这是对资金语义的实质改动，建议在第 1、2、4、5 项都完成、并且热点企业的实际流量证明仍然不够时，再单独设计和评审。

## 局限

- 只有一台共享开发机。PostgreSQL、Redis、Worker、全部 Relay、上游替身和客户端都运行在同一台机器上，测量期间还有其他会话的虚拟机和测试在运行。M5 的性能核和能效核速度不同，单线程 Worker 的速度会随调度变化。没有真实网络往返、TLS 终止层和跨地域延迟，也没有真实厂商上游。**这些数据不代表部署环境的容量。**
- 应用户要求，为了避免主机过载，本次在运行完全部场景之前就停止了：
  - 快照场景只有一轮；
  - 故障转移只有冒烟运行的一轮数据，那一版脚手架还没有记录输入速率和运行期间其他进程的 CPU；
  - 本地分词估算器没有运行；`hotwallet`（Worker 暂停对照）后来补跑，见[Worker 优化后](#worker-优化后)。

  这些都可以用上面的命令补测，建议在专用机器或部署环境中进行。
- 有 ⚠ 标记的轮次，重跑后仍然受到主机负载影响。它们的结果偏差在一个方向上：延迟偏高、成功数偏低。
- `pg_blocking_pids` 和 Worker 事务时长这两项采样是在正式运行开始后才加入的，所以本次数据都不包含它们。

## 优化后

本节记录对准入路径的优化（第一、二阶段：上文[优化建议](#优化建议)第 1、2、3、5、6、7 项，以及[瓶颈](#瓶颈分析)第 1、3、4 节）。结算吞吐（瓶颈 2、建议 4、8）见[Worker 优化后](#worker-优化后)。所有改动都不改变资金语义：每个改动点按什么规则扣费、什么时候进入核对，见各小节。

### 慢客户端的交付判定（设计说明）

**原来的问题。** 上游结束后，Relay 等终态块写出的时限固定为 30 秒，从上游结束时起算，写出有进展也不重置。上游结束时还有数据积在 Relay 的通道（最多 2 个事件）、hyper 的写缓冲和内核发送缓冲里，客户端读完这些数据之后终态块才能写出。客户端读得慢但一直在读时，30 秒到期就判为 `delivery=unknown`，请求进入 review，尽管客户端最后收到了完整的流。

**新的规则。**

- **写出进展**：该连接的 socket 被写入的字节数增加，即 `poll_write` 把数据交给了内核。
- **按进展计时**：两处改为“`NEXUS_RELAY_STREAM_IDLE_MS`（默认 30 秒）内没有任何写出进展才超时”，有进展就继续等：
  - 向客户端排队每一个事件；
  - 上游结束后等待终态块写出。
- **总上限**：为了不让一次只读几个字节的客户端无限占用节点，一次等待最多持续 10 倍空闲时间（默认 5 分钟）。
- **WebSocket**：每条消息的写出、每轮等待终态帧写出，按同样的规则判定。
- **没有采用“限制 Relay 侧排队字节数”的方案**：Relay 自己的队列本来就有界（2 个事件），慢客户端的背压已经传到上游。积压在内核发送缓冲里，缩小它会降低正常客户端的吞吐，也不改变判定。

**各种情况的判定和扣费。** “成功交付”的定义没有变：终态块写进了 socket。改动只决定 Relay 愿意为它等多久。

| 情况 | 交付判定 | 资金 |
| --- | --- | --- |
| 客户端读得慢但一直在读，终态块在 5 分钟上限内写出 | `succeeded`（原来超过 30 秒就是 `unknown`） | 按用量扣费，与快客户端相同 |
| 客户端一直在读，但 5 分钟上限到期时终态块仍未写出 | `unknown` | 预留保留，进入核对 |
| 客户端停止读取超过 30 秒（上游结束前或结束后） | 上游结束前：流中断；结束后：`unknown` | 预留保留，进入核对（与原来相同） |
| 客户端断开连接 | 写出失败，`unknown` | 同上 |
| 上游中途断开 | 不受影响 | 与原来相同 |
| 非流式（JSON）响应 | 不受影响：原来就等到写完或连接关闭 | 与原来相同 |

**保守原则。** 只有终态块确实写进 socket 的流，才会从 `unknown` 变为 `succeeded`；其余仍是 `unknown`，进入核对，不会因为这个改动多扣钱。字节写进内核并不等于客户端收到，这个限制与快客户端相同，没有扩大。

### 改动

**1. 准入时不再展开快照（建议 2）。**

- **索引表**：发布时 publication 写两张按键建索引的表。
  - `publication.snapshot_index`：每个修订的路由（企业, 模型）、部署、模型和企业的访问策略，主键 `(cluster_id, revision, kind, primary_id, secondary_id)`。
  - `publication.cluster_keys`：集群的 Key，按 `(cluster_id, key_id, added_sequence)` 建主键，另有 `(cluster_id, key_id)` 的存活唯一索引。
- **模块边界**：billing 和 gateway 不直接 JOIN 这些表，只调用 publication 授权给 `nexus_bridge` 的 `publication.v1_admission(principal, rev, kid, org, model, for_admission)`。
- **形状不变**：它返回 Key（按该修订的 Key 序号判断是否属于集群），以及与快照同形、只含该企业相关路由、部署、模型和访问策略的清单。catalog 的资格检查函数原样使用。
- **开销**：`reserve_*`、`start_attempt`、`preflight` 都改走这条路径，每个请求的数据库开销与 Key 数、企业数和部署数无关。
- **顺带去掉的开销**：`get_credential_envelope`（每个请求的第一条 SQL）和 `ack_config` 原来也调用 `v1_snapshot`、展开整个快照并做 Base64，现在只读快照行的几个列。

**2. 条件拉取，Key 增量下发（建议 3）。**

- **轮询**：节点每 2–3 秒调用 `config_head`，只返回修订、摘要、Key 序号和本节点已应用的修订；与本地一致就不再读取。变化时 `get_config_snapshot(revision)` 返回存储的原文（bytea），不再附带 manifest 和 Base64。
- **Key 的处理选了增量下发**，理由：
  - 撤销的检测是确定的：撤销推进源修订，自动发布生成新修订，下一次 `config_head` 就能看到，与原来全量拉取的时限相同。回查方案要靠正缓存的 TTL 或单独的撤销通道才能发现撤销。
  - 请求路径上没有额外的数据库往返，也没有可被拿来枚举 Key 的查询入口，不需要负缓存和限速。
  - 节点内存仍随 Key 数线性增长，但每个 Key 只是一个约 200 字节的条目，10 万个 Key 约 20 MiB，原来是 409 MiB 的完整 JSON。
- **序号的来源**：序号不是 identity 的全局序号，而是 publication 在发布时按集群分配的。企业、项目、服务账号的状态变化和集群范围变化都会让 Key 进出集群，只有在发布时与上一个 Key 集合求差，才能同时覆盖这些情况；identity 的单个 Key 序号表达不了这些变化。
- **校验和自愈**：快照的 `key_set` 带 Key 数和集合摘要，节点按净变化更新后核对两者，不一致就从序号 0 重新读取全部 Key。
- **回滚语义的变化**：回滚恢复旧的模型、部署、路由和策略，Key 集合保持当前。原来回滚会把回滚点之后签发的 Key 一并移出集群。
- **撤销与范围失效的检测仍然保留**：
  - `config_head` 对期望快照做与原来全量读取相同的范围检查，集群范围失效（`snapshot_scope_expired`）时直接报错，节点标为不健康。
  - Key 撤销通过新修订和 Key 增量送达。
  - 测试覆盖：`test_relay_admission.py::test_polling_reads_only_the_head_and_still_sees_revocation_and_scope_expiry` 用 PostgreSQL 语句日志证明空闲时只调用 `config_head`、不读原文和 Key，并验证新 Key 生效、撤销的 Key 被拒绝、范围收缩后 `/ready` 变为 503；`test_plane.py` 的范围收缩用例对 `config_head`、`get_config_snapshot`、`config_keys` 都断言 `snapshot_scope_expired`。

**3. 合并 `reserve_request` 和 `start_attempt`（建议 5）。**

- **合并调用**：各 `reserve_*` 末尾增加 `aid`、`dep`。`gateway_v1.admit` 在同一事务里预留并登记第一次尝试，企业串行区只进入一次，只有一次往返和一次同步提交。故障转移的后续尝试仍调用 `start_attempt`。
- **取消语义**：尝试登记失败时整个事务回滚，不留下预留，等价于原来“预留后立即取消”。
- **重放语义**：同一 rid、aid 和参数重放时，返回已提交的请求并按 `start_attempt` 的规则重放尝试；结果仍未知时，先取消（只有预留时生效），已有尝试则以 `unknown` 关闭进入核对，与原来开始尝试结果未知时相同。
- **有意保留两步的情况**：WebSocket 的第一轮要先拨通上游，仍然先预留，拨通后再 `start_attempt`，拨号失败时可以干净地取消预留。消息批处理本来就在一个事务里完成两步。
- **一处可见差异**：客户端恰好在合并调用进行中断开时，第一次尝试已经登记，于是以“未发送”关闭。客户不扣费，该尝试进入 `missing_usage` 成本核对。这与原来“开始尝试后、发送前断开”的路径相同；原来在预留和开始尝试之间断开时可以直接取消。现在发起调用前会先检查客户端，断开的不再预留。
- **测试覆盖**：`test_indexed_admission.py::test_first_attempt_commits_with_the_reservation` 覆盖整体回滚、重放、错误尝试的拒绝和不可取消。原有的 `lose_gateway_receipts` 故障注入（`test_relay.py`、`test_relay_streams.py`、`test_relay_conversion.py`、`test_relay_compact.py`）现在丢弃的是合并调用提交后的应答，验证了合并后的重放。

**4. 配置刷新改用独立连接（建议 6）。**

- **独立连接**：维护循环使用主连接池之外的一个连接，读 head、原文、Key 增量、凭据包，并写确认。
- **行锁也要改**：只换连接还不够。每个 gateway 调用的 `v1_principal` 原来对集群行和节点行取 `FOR SHARE`，排队等企业锁的准入会一直持有它。于是发布时更新集群行（`desired_revision`、`distributed_revision`）、节点确认时取节点行的 `FOR UPDATE`，都会被几百个排队的会话挡住。原 10 万 Key 场景的“分发失败”和本次基线重跑时的失败都是这个原因。现在准入只取 `FOR KEY SHARE`，确认取 `FOR NO KEY UPDATE`，发布锁集群行用 `FOR NO KEY UPDATE`，更新非键列不再等排队的准入。
- **对停用的影响**：停用集群或节点也不再等待在途调用结束，在途调用最多晚几毫秒提交，此后的调用都会被拒绝。
- **`/ready` 的选择：连接池耗尽时不退出负载均衡。** 理由：
  - 连接池耗尽几乎总是所有节点共有的数据库争用。摘掉节点不减轻数据库负载，只把请求推给其余节点，还可能让整个集群同时显示为不可用。
  - 单个请求拿不到连接时等 5 秒返回 503。热点企业由准入名额限流（第 5 项）。
  - `/ready` 只在配置刷新失败或节点并发已满时返回 503。
- **测试覆盖**：`test_relay_admission.py::test_refresh_keeps_its_own_connection_when_the_pool_is_exhausted` 用 1 个连接的连接池，让请求等在企业锁上，同时发布新修订，验证节点照常应用并确认、`/ready` 始终为 200。

**5. 连接治理与企业级并发上限（建议 1）。**

- **连接预算**：`NEXUS_RELAY_POOL_SIZE` 的公式写进了 Helm values 和[部署文档](deployment.md#连接预算)。CNPG 的 `max_connections` 按 `节点数 × (连接池 + 1) + API + Worker + 余量` 计算，chart 默认值 16 × 9 + 2 × 5 + 1 × 5 + 30 = 189 ≤ 200（Worker 默认改为 2 个副本后为 194）。本机没有 helm，没有运行 `helm lint`，只改了 values 和注释。
- **`statement_timeout`**：改为角色设置。relay-node Job 的 `ensure_gateway_login` 对节点登录执行 `ALTER ROLE … SET statement_timeout = '8s'`，Relay 不再在 `after_connect` 里 `SET`，启动时发现值为 0 就拒绝启动。PgBouncer 的 transaction 模式下也能生效。
- **现有 `concurrency` 配额不能用来限制排队的会话**：它限制的是在途请求，从预留一直持有到流结束，超限立即返回 429。压到“节点数 × 2”这个量级，就同时把企业的长流并发压低了。
- **新增的准入名额**：一个集群范围的 Redis 有序集合，只在准入调用期间持有，默认 `NEXUS_RELAY_TENANT_ADMISSIONS=32`。企业的 platform 层 `admission_concurrency` quota policy 覆盖它，沿用 `quota_policies` 和资源数量那套 platform 层、企业范围的约束。没有名额的请求在节点内存中排队，每个节点每个企业只有队首轮询 Redis，等待超过 `NEXUS_RELAY_ADMISSION_WAIT_MS`（5 秒）返回 429，没有预留。
- **测试覆盖**：`test_relay_admission.py::test_admission_slots_bound_the_sessions_queued_in_the_database` 验证名额为 1 时，3 个并发请求只有 1 个会话进入数据库等锁，另外两个返回 429；platform 层覆盖为 3 后，3 个会话都进入；customer 层的覆盖返回 422。

**6. 慢客户端按写出进展判定交付（建议 7）。** 见上面的设计说明。测试覆盖：`test_relay_admission.py::test_a_slow_reader_that_keeps_reading_receives_and_pays_for_its_stream` 中，客户端持续慢读一个 4 MiB 的流，上游结束后还需要读超过 1 秒的空闲时限，交付判为 `succeeded` 并正常扣费。`test_relay_streams.py::test_slow_downstream_keeps_lease_until_bounded_abort` 中完全停读的客户端仍在空闲时限后中止，进入核对，不扣费。`delivery.rs` 的单元测试用暂停的时钟覆盖进展、停滞和总上限三种情况。

**先更正一个结论：64 个节点 × 8 个连接时，突发请求的 503 来自 macOS 的监听队列，不是锁等待。** 原报告把 186–188 个 503 归因于“连接池超时”。这次逐个检查：

- **失败的特征**：这些请求都在突发开始后 20 ms 内失败，在第一条 SQL（`get_credential_envelope`）上报 `kind=unavailable`，PostgreSQL 日志里没有任何对应的错误。
- **原因**：节点刚重启时，每个节点在第一次突发里同时新建约 7 个连接，64 个节点一共约 450 个连接同时发起。macOS 的 `kern.ipc.somaxconn` 为 128，超出的连接在 TCP 层直接被重置（ECONNRESET），请求根本没有到达 PostgreSQL。
- **复现**：同时向本机 PostgreSQL 发起 450 个 TCP 连接，217 个被重置。

## Worker 优化后

本节对应[瓶颈 2](#2-单个-worker-的结算吞吐)和[建议 4、8](#优化建议)，在 2026-11-15 于同一台 Apple M5（10 核，16 GiB）上测量。原始数据见各小节说明，数据只代表这台共享开发机。

### 结论

- **没有哪次提交让 Worker 变慢。** 同一个基准在 `a9ca0c2`（Python 基线）和 `fb54210`（优化前）上结果相同：每笔 20 条 SQL（该基准没有预算）、约 2.9 ms CPU，单个 Worker 进程每秒清空 240–280 笔。P5 中“每笔 7–13 ms CPU、每秒 45–143 笔”是测量方式和环境叠加的结果：CPU 按 profile 窗口计算，包含空闲轮询；能效核让 CPU 时间翻倍；突发时 PostgreSQL 被 500 个节点会话占满，而一笔结算要往返 25 次。
- **开销在 SQL 往返和 ORM，不在计费逻辑。** 一笔结算是一个事务、25 次往返；归一化、计价和摘要合计不到 0.1 ms。
- **按钱包批量结算**：一个事务结算一个钱包最多 32 笔，读写都按批进行，判定和过账代码不变。进程内每笔 CPU 从 3.1–3.7 ms 降到 0.63–0.71 ms，每秒 204–246 笔升到 1,014–1,128 笔；压测中突发后的积压清空从每秒约 260 笔升到 1,340–1,560 笔，突发结算 p99 从 1.2–1.9 秒降到 0.3–1.1 秒。单笔失败时整批回滚、逐笔重做，只有失败的那笔重试。
- **热点钱包**：补跑的 `hotwallet` 场景表明，Worker 锁钱包行是热点预留尾延迟的主因（p99 多 3–7 ms），backlog 扫描是次要因素（p50 多约 0.2 ms）。批量结算后 Worker 持有钱包的总时间约为原来的 1/5，但单次更长，热点稳态 `reserve_request` p99 高 1–2 ms。backlog 检查改为读一行计数，不再在企业锁内扫描队列。
- **故障转移**：Relay 只在上一次尝试被证明没有执行时才换部署，所以被换掉的尝试改为按零成本确认。主部署持续返回 429 时，核对事项从每个请求一个（1,000 个）变为 0。另外新增尝试结果 `declined`；按部署和时段汇总剩余核对事项没有实现，原因见下文。
- **多 Worker**：并发测试覆盖乱序、重放、并发领取、同一钱包并发、会话中途丢失和进程被杀，重复扣费和漏扣都是 0。测试中发现并修复了批量结算引入的锁顺序死锁。chart 默认 2 个副本。
- **backlog 上限**默认值改为 2,048，不随 Worker 数量放大；积压时拒绝新预留的语义保留。

### 每笔结算花在哪里

`tests/integration/test_settlement_capacity.py` 按 Relay 的方式写入事实：用节点登录调用 `reserve_request`、`start_attempt`，再写 `openai.responses.v1` 格式的 `attempt.finished` 和 `request.closed`。写入期间不运行 Worker，然后在同一进程里用 Worker 的角色和连接池执行 `UsageProcessor` 清空队列，统计每笔的墙钟和 CPU、客户端执行的语句数和耗时、服务器为 Worker 登录记录的语句（含 BEGIN、COMMIT 和连接池探活），并用 cProfile 拆分各阶段。8 家企业、90% 热点，600 笔。

```sh
SETTLEMENT_BENCH=1 LC_ALL=en_US.UTF-8 TMPDIR=/tmp/nx \
  uv run python scripts/run_integration.py --capacity -s -q tests/integration/test_settlement_capacity.py
```

优化前（`fb54210`）一笔结算是一个事务，往返 25 次：

| 步骤 | 语句 |
| --- | --- |
| 事务开头 | 连接池探活、BEGIN、`SET LOCAL ROLE`、`SET LOCAL search_path`、读账务策略行 |
| 领取 | 选钱包（`FOR UPDATE OF a SKIP LOCKED`）、锁请求、锁并复查任务 |
| 读事实 | 尝试和成本价（`FOR UPDATE`）、成本更正、用量事件、售价和折扣、预算占用（`FOR UPDATE`） |
| 写入 | 确认尝试成本、审计、归一化记录、钱包、预算占用、预算期间、流水、`clock_timestamp()`、请求、审计、任务状态，各一条；ORM 每次 `edit` 都立即 flush |
| 结束 | COMMIT |

单笔开销（load1 3–9 时的多轮范围）：墙钟 3.5–5.7 ms、CPU 2.9–4.4 ms。其中服务器执行全部语句只要 0.4–0.7 ms，客户端等待语句（含往返）1.9–2.5 ms，其余是 SQLAlchemy ORM、psycopg 和事件循环在每条语句上的开销。归一化（0.02 ms）、计价（0.05 ms）和摘要（0.02 ms）可以忽略：开销与业务逻辑无关，几乎全部随语句条数增长。

### 是否有提交让它变慢

用同一个基准（单个企业、`fixture.tokens.v1`、600 笔，先进程内清空，再启动真实的 Worker 进程清空）在 `a9ca0c2`（0012 优化后，即 Python 基线）和 `fb54210` 上交替运行：

| 提交 | 进程内：语句/笔、墙钟 ms、CPU ms、笔/秒 | Worker 进程：笔/秒、CPU ms/笔 |
| --- | --- | --- |
| `a9ca0c2` | 20、3.55–4.21、2.88–3.38、238–282 | 147–278、2.86–5.30 |
| `fb54210` | 20、3.56–3.71、2.86–2.96、270–281 | 114–273、2.90–6.60 |

两者没有差别，语句数也相同。0012 之后 Worker 从 6 个消费者增加到 11 个，空闲时的 CPU 只从 0.08 核升到 0.09 核。两个提交都出现过 CPU 翻倍的轮次（5.3 ms 和 6.6 ms），这是 M5 把单线程 Worker 调度到能效核上的结果。

P5 报告的“每笔 7–13 ms CPU、积压时每秒 45–143 笔”由以下因素叠加而成，不是某次提交引入的退化：

- 每笔实际约 3–4.4 ms CPU，主机繁忙时更高；
- P5 用 profile 窗口内的 Worker CPU 除以结算笔数，窗口里还有空闲轮询：0.09 核在 50 请求/秒时折合每笔约 2 ms；
- 能效核让 CPU 时间翻倍；
- P5 的突发 profile 中，PostgreSQL 同时承受 500 个节点会话（1.6–2.8 核），Worker 每次往返都更慢，而一笔结算有 25 次往返；
- Python 基线（290–390 笔/秒）是在 1–8 个模拟节点、主机较空闲时测得的。

### 热点钱包：Worker 锁钱包和 backlog 扫描各占多少

`hotwallet` 场景（64 个节点、每节点 8 个连接、90% 热点、50 请求/秒、1,000 个请求）在优化前补跑了两轮，主机较空闲（load1 3–4，其他进程 46–92%）：

| profile | reserve p50 / p95 / p99 ms | start_attempt p99 ms | 上游前 p99 ms | 积压 |
| --- | ---: | ---: | ---: | ---: |
| worker-running | 0.9–1.6 / 4.6–6.5 / 5.8–9.6 | 6.3–7.5 | 13.2–18.7 | 0–3 |
| worker-paused | 1.1–1.2 / 1.9–2.4 / 2.2–2.7 | 1.4–1.8 | 7.6–8.2 | 增长到 1,000 |

- **Worker 锁钱包是主因。** Worker 运行时，`reserve_request` p99 多 3–7 ms，`start_attempt` p99 多约 5 ms。`pg_blocking_pids` 采样里阻塞节点会话的是 `nexus_worker:idle in transaction`：Worker 的结算事务持有热点钱包的行锁，同一企业的预留和开始尝试在企业锁内等它。
- **backlog 扫描是次要因素。** Worker 暂停时队列从 0 涨到 1,000，触发器每次预留扫描的任务数随之增加，`reserve_request` p50 只从约 0.9 ms 升到 1.1–1.2 ms。单独测量，扫描 1,024 个 ready 任务在紧凑的表上需要 0.05–0.07 ms，任务行被反复更新后更慢。它在企业锁内，但不是延迟的主要来源。

### 优化方案

**1. 按钱包批量结算。** 一个事务取最早到期任务的钱包（`FOR UPDATE OF a SKIP LOCKED`），再取这个钱包最多 32 个到期任务（`FOR UPDATE OF r, j SKIP LOCKED`）。先按请求 ID 锁住它们的报表变更行，再把这些请求的尝试和成本价、成本更正、用量事件、售价、折扣、预算占用各用一条查询读出。之后逐笔执行原来的判定和过账代码：归一化、确认尝试成本、客户费用、预算、流水、审计、核对项，代码路径与单笔结算相同，只是写入先留在 ORM 会话和一个语句队列里，最后一次写出（同类 UPDATE 用 executemany，INSERT 合并成一条）。一批共约 21 条语句，与条数无关。

收益（进程内基准，两棵代码树在同一主机上交替各跑两轮，load1 3.0–5.1）：

| profile | 每笔墙钟 ms | 每笔 CPU ms | 每笔客户端语句 | 进程内清空 笔/秒 | 核对事项 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单次尝试，90% 热点 | 4.11–4.91 → 0.89–0.99 | 3.13–3.71 → 0.63–0.71 | 22 → 1.55 | 204–244 → 1,014–1,118 | 0 → 0 |
| 单次尝试，均摊 | 4.07–4.72 → 0.89–0.92 | 3.08–3.64 → 0.63–0.65 | 22 → 1.59 | 212–246 → 1,091–1,128 | 0 → 0 |
| 先被拒绝、再换部署成功 | 4.43–7.25 → 1.32–1.50 | 3.31–5.06 → 0.97–1.11 | 24 → 1.78 | 138–226 → 667–756 | 600 → 0 |

每笔的 CPU 降到原来的约 1/5，客户端往返从每笔 25 次降到每批约 24 次（含探活、BEGIN、COMMIT），平均每笔不到 2 次。剩下的时间主要在等待数据库。报表投影每笔另需约 0.12 ms CPU，没有变化。

风险及处理：

- **一笔失败拖累整批。** 任何一笔抛出异常（成本冲突、结算冲突、数据库错误），整批回滚，然后把这批请求逐个放进单独的事务重新结算。只有再次失败的那一笔按原来的退避重试（`failures`、`next_attempt_at`、`reason='processing_retry'`），其余照常完成；异常仍向消费者循环抛出，健康检查和日志与以前一样。代价是失败时这一批要重做一次。`test_one_failing_request_does_not_hold_back_its_batch` 覆盖这条路径。
- **预算期间。** 每笔请求仍结算到授权时记录的预算占用和期间。同批请求共用的期间行在一个会话里只有一个对象，扣减按顺序累加，最后写一次；跨日或跨月的请求各自对应不同的期间行。钱包流水序号按处理顺序递增，`balance_after` 逐笔计算，余额检查（`B - C >= H`）也逐笔执行。
- **锁的持有时间。** 一批持有钱包行锁的时间比一笔长：稳态下 Worker 每 100 ms 醒来一次，一批只有几笔；积压时一批 32 笔。在钱包上等待的预留最多等一批。Worker 持有钱包的总时间约降为原来的 1/5，但单次更长，热点稳态下 `reserve_request` 的 p99 因此略升（见下文对比），`start_attempt` 的 p99 和上游前开销下降。
- **结算时间戳。** `settled_at` 取领取这一批时的 `clock_timestamp()`，比提交早最多一批的时长；流水的 `posted_at` 仍由数据库在插入时生成。
- **崩溃。** 一批在一个事务里，进程中途退出时全部回滚，没有部分写入。
- **新的锁顺序。** 一批会更新多个请求的尝试和请求行，它们的报表触发器按 ORM 写出的顺序（尝试 ID 顺序）锁 `billing.report_changes` 行；同一进程里的报表投影按请求 ID 顺序确认这些行。两者会互相等待，PostgreSQL 在 `deadlock_timeout`（1 秒）后中止其中一个。第一轮对比数据中有两轮出现约 1 秒的 Worker 事务（`steady-8n-uniform` 结算 p99 0.79 秒，2 个 Worker 的 `worker-paused` 清空 2.93 秒），保留工作区重跑后在 PostgreSQL 日志中看到了这两种语句之间的 `deadlock detected`。被中止的是结算批，随后逐笔重做，金额没有受影响，但结算停顿约 1 秒。现在每批先按请求 ID 顺序锁住这些行。`test_batch_and_report_projection_take_report_rows_in_one_order` 构造了这种交错：去掉这一步时 0.75 秒后报 `deadlock detected`，加上后立即完成。下文的对比数据是修复后重跑的。

**2. backlog 检查移出企业锁内的扫描。** 触发器 `billing.check_settlement_backlog` 不再每次预留都扫描最多 1,024 个 ready 任务，而是读单行计数 `billing.settlement_backlog`。计数早于 100 ms 时，由发现它的那个预留重新计数（最多数到阈值），其他预留用 `SKIP LOCKED` 跳过、沿用上次的值。每秒最多扫描 10 次，其余预留只读一行。计数由预留自己维护，所以 Worker 全部停止时背压照样生效（`test_backlog_replay_and_worker_takeover`）。代价是阈值最多滞后 100 ms。

**3. 被换掉的尝试按零成本确认。** 见下文“故障转移”。

**4. Worker 的部署。** chart 默认 2 个副本，按主机分散，带 PodDisruptionBudget。Worker 连接设置 `idle_in_transaction_session_timeout=30s`：领取就是事务里的行锁，宿主消失而连接没有关闭时，最多 30 秒后由 PostgreSQL 结束会话、释放钱包，而不是等 TCP keepalive（默认两小时）。

### 故障转移的核对事项

Relay 在 `upstream::refusal` 中把上游的 429、503、529 分成三类：`Declined`（厂商文档列明的准入拒绝，例如 OpenAI 的 `rate_limit_exceeded`、`server_is_overloaded`，Anthropic 的 `rate_limit_error`、`overloaded_error`，Bedrock 的 `ThrottlingException`），`Refused`（信封中类型未列明的 429），`Unknown`（其他，例如中间层的 502）。连接没有建立、签名失败也算没有发出。但上报时，`Declined` 和 `Refused` 的尝试都记为 `outcome: "failed"`、`raw_usage: null`，与执行中出错的失败尝试（上游 5xx 错误信封、`response.failed`、Bedrock 错误）没有区别；`Unknown` 记为 `unknown`。所以控制平面不能只凭 `failed` 判定“没有执行”。

可以作为证明的是尝试序列：Relay 只在 `Opened::Declined` 分支调用 `fail_over`，只有 `fail_over` 会开始序号大于 1 的尝试，而且先提交新尝试、再上报旧尝试的 `attempt.finished`。因此，一个没有用量的 `failed` 尝试只要之后还有同一请求的尝试，就是 Relay 证明了没有执行的尝试。Worker 对这种尝试按零成本确认（归一化规则 `relay.declined/1`，成本 0，写审计 `attempt.cost_confirmed`），不再开 `missing_usage` 核对项。这条约定写进了[协议](plane-protocol.md#用量事件)。另外新增了尝试结果 `declined`，`raw_usage` 只能为 null 或全零，Worker 同样按零成本确认；Relay 当时还不会发送它（Relay 不在本次修改范围内），之后已改为发送，见下。

仍然逐个核对的情况：
- 最后一次尝试被拒绝（没有备用部署、达到 `max_attempts`、故障转移预算用完）：线上仍是 `failed` 加 null，无法与执行后的失败区分。已修改：Relay 现在对这类尝试（以及已登记但没有发出的备用尝试）上报 `declined`，这部分核对已经消失。
- `Refused`、执行中出错、未知结果：可能已经执行并计费，需要按尝试对照账单。

按部署和时段汇总这些剩余事项没有实现。现在每个核对事项都绑定一个尝试，财务用这个尝试的账单（`confirm_cost`）或用量（`supplement_usage`）关闭它；汇总需要新的批量决定动作，会改动管理 API、OpenAPI 快照和控制台，超出结算侧。主部署持续返回 429 且有备用部署时（P5 的场景），新逻辑下已经没有剩余事项。

### backlog 上限

`settlement_backlog_limit` 是全库 ready 任务数的阈值，达到后节点的新预留返回 `settlement_backlog`（503）。它的作用是在 Worker 跟不上或全部停止时止损：拒绝发生在预留之前，不占用资金；已授权的请求照常上报、重放和结算；积压降到阈值以下后自动恢复。这个语义合理，应当保留，但有一个缺点：阈值是全局的，一个热点企业的积压会让所有企业的新预留一起被拒绝。按企业的上限更公平，但需要在企业锁内按企业计数，可以等出现实际问题再做。

**默认值从 1,024 改为 2,048。** 优化前单个 Worker 每秒清空 100–270 笔，1,024 笔要 4–10 秒，已经接近结算 p99 ≤ 5 秒的目标。优化后单个 Worker 每秒清空一个钱包 1,340–1,560 笔，2,048 笔约 1.5 秒；主机繁忙、Worker 被调度到能效核上慢一倍时约 3 秒，仍在目标之内。积压达到这个量说明输入已经持续超过结算能力，再放宽只会让结算延迟变长，所以没有改得更大。部署方可以按“可接受的清空秒数 × 单个钱包的清空速度”调整。

**不按 Worker 数量自动放大。** 一个钱包同一时刻只能由一个 Worker 结算，积压集中在热点钱包时增加 Worker 不会更快（上表 90% 热点时 1 个和 2 个 Worker 的清空时间相同），所以阈值应按单个 Worker 的速度设置。数据库也不知道当前有几个 Worker 存活（心跳在 Redis 中）；Worker 全部停止时，阈值保持不变、新预留在积压达到阈值后被拒绝，这正是需要的行为。

**检查不再在企业锁内扫描队列。** 见上文优化 2。阈值因此最多滞后 100 ms，可能多放行约 0.1 秒的输入。

### 其他发现和未完成的部分

- **钱包核对持有钱包行锁。** Worker 每小时对每个钱包运行一次 `check_account`：先 `FOR UPDATE` 锁住钱包，再把该钱包的全部流水和请求读进 Python 核对。压测中一个钱包有几千笔请求时，这一步要约 1 秒，期间这家企业的预留和结算都要等待；历史越长越慢。已修改：核对先领取 `billing.account_checks` 的租约，再在 REPEATABLE READ 只读快照中比较，不再锁钱包；逐条流水检查改为增量，见[财务核对](operations.md#财务核对)。
- **剩余的成本核对事项没有按部署和时段汇总。** 理由见[故障转移的核对事项](#故障转移的核对事项)。
- **Relay 还不发送 `declined`。** 最后一次被拒绝的尝试仍会各开一个核对事项，需要 Relay 在 `upstream::refusal` 判为 `Declined` 或请求没有发出时上报 `declined`。已修改：Relay 现在上报 `declined`。
- **主机负载。** 优化后的压测与另一个会话的测试同时运行，load1 比优化前高 1–4（control 组第一次运行时达到 12–29，已重跑），准入相关的数字因此偏高；Worker 相关的数字（清空速度、Worker CPU）差距远大于主机负载的影响。`helm lint` 没有运行：本机没有 helm。
