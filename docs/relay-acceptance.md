# Relay 容量验收（P5）

本报告对应[开发计划](relay-development.md#阶段依赖与交付)的 P5 行和其后的“负载口径”。测量对象是 release 构建的 Rust Relay（`nexus-relay`），而不是[控制平面验收](control-plane-acceptance.md)中的 Python 网关模拟器。数据只代表下文这台共享开发机和本地 TLS 上游替身，**不能当作部署环境的容量**：没有真实网络往返、真实上游和跨地域延迟，PostgreSQL、Redis、Worker、全部 Relay、上游替身和压测客户端运行在同一台机器上，并且与其他会话的任务共享 CPU。

## 结论

- **结算目标（p95 ≤ 2 秒、p99 ≤ 5 秒）只在部分场景达到。** 达到的场景：4 个节点下 HTTP、SSE、WebSocket、故障转移的常规负载；64 个节点、90% 热点企业的稳态，在每个节点的连接池降到 2 时也能达到（p99 0.53–1.23 秒）。8 个节点 50 请求/秒时，p99 为 2.27–9.71 秒，各轮差异很大，取决于主机负载。按默认配置（每个节点 8 个连接）未达到的场景：64 个节点的稳态（热点 p99 3.30–9.15 秒，均摊 7.46–8.47 秒），以及 64 个节点同时突发 512 个请求（均摊 p99 5.49–11.0 秒；热点有 48–188 个请求返回 503）。范围中数值较大的一端多数出现在主机繁忙的轮次。
- **Relay 进程本身不是瓶颈。** 50 请求/秒时，全部 64 个 Relay 合计只用 0.1–0.17 个核；普通请求下每个进程 RSS 为 14–35 MiB。4 个节点转发 count_tokens 时可以达到每秒 3,000–4,000 个请求。100 路同时持续 30 秒的 SSE 长流、200 个空闲 WebSocket 连接和慢客户端，都没有让内存失控。
- **集群容量在这台机器上受三处限制，三处都在 Relay 之外**：
  1. **热点企业的预留串行，叠加节点连接数。** `reserve_request` 和 `start_attempt` 都要先取企业级 advisory lock。64 个节点、每节点 8 个连接时，最多有约 500 个会话排队等同一把锁。排队超过 5 秒后，节点拿不到连接池连接，第一条 SQL（`get_credential_envelope`）就失败，请求返回 503。热点企业还会占满节点的连接，连带阻塞同一节点上其他企业的请求。把连接池从 8 降到 2，512 个热点突发请求从 324–326 个成功变为全部成功；延长 `deadlock_timeout` 没有改善。
  2. **单个 Python Worker 的结算速度。** 每结算一笔约需 7–13 ms CPU，积压时清空速度约为每秒 45–140 笔。持续输入超过这个速度后，积压达到 `settlement_backlog_limit`（1,024）时，新的预留会被拒绝。实测 Messages 以每秒约 1,080 个请求输入时，约 46% 的请求返回 503。
  3. **快照规模。** 每次预留和开始尝试，都会在 SQL 里展开整个快照，并对 Key 列表做线性扫描。节点每 2–3 秒还会拉取一次完整快照。1 万个 Key 时，`reserve_request` 的 p50 从 1.5 ms 升到 13.9 ms，每个 Relay 的 RSS 升到约 96 MiB。10 万个 Key 时，单次拉取需要 0.84–1.56 秒，每个 Relay 的 RSS 达到 409 MiB，20 请求/秒的负载全部失败。这组数据只有一轮，而且运行时主机较忙。
- **资金一致性**：全部 profile 都完成了核对，67,960 个已扣费请求中，重复扣费、漏扣和金额错误都是 0。预留要么归零，要么按设计进入 review：故障转移中失败的尝试、WS 中途断线，以及被中断的慢客户端流。
- **大致容量（只代表本机和本地上游替身）**：
  - 单个 Relay 节点的 CPU 足以处理每秒上千个普通请求，实际上限由 PostgreSQL 决定。
  - 集群可以持续承受约 50 请求/秒并满足结算目标，前提是每个节点连接池 ≤ 4，并且主机不被其他任务占满。
  - 单个 Worker 的结算速度约为每秒 100 笔，这是集群的持续吞吐上限。
  - 单个企业的串行预留在连接池为 2 时可以处理每秒约 150–400 个请求，但同一时刻排队的会话数必须受到限制。
- **建议**按收益和成本排序：
  1. 按“节点数 × 连接池 ≤ PostgreSQL 核数的 2–4 倍”设置连接池，64 个节点时设为 2；
  2. 把准入 SQL 中的快照展开换成按 Key 的索引查找，并让节点只在修订变化时才拉取快照；
  3. 合并 `reserve_request` 和 `start_attempt`，并让 Worker 能够水平扩展；
  4. 给节点预先分配额度的风险较高，只适合作为最后手段。

  详见[瓶颈](#瓶颈分析)和[建议](#优化建议)。

本次运行没有修改产品代码。找到的瓶颈要么需要协议或迁移层面的改动，要么会影响资金或交付语义，都不属于“小而安全”的修复，因此只写入建议。

## 复现

```sh
mkdir -p /tmp/nexus-p5
TMPDIR=/tmp/nexus-p5 LC_ALL=en_US.UTF-8 \
  uv run python scripts/relay_load.py --out /tmp/nexus-p5/report
```

`TMPDIR` 必须是短路径：PostgreSQL 的 Unix socket 路径不能超过 103 字节。macOS 上需要 `LC_ALL=en_US.UTF-8`，否则 PostgreSQL 会以 “postmaster became multithreaded” 退出。`--scenarios control,pools,hotwallet,http,ws,tokens,snapshot,failover` 选择场景，`--rounds` 设置轮数（默认 2），`RELAY_LOAD_PROFILES=子串,…` 只运行名称匹配的 profile，`RELAY_LOAD_SNAPSHOT_KEYS`、`RELAY_LOAD_SNAPSHOT_NODES` 调整快照场景。开发时可以加 `--workspace DIR --keep` 复用服务。

脚手架由以下文件组成：

| 文件 | 作用 |
| --- | --- |
| `scripts/relay_load.py` | 构建 release Relay；启动隔离的 PostgreSQL 和 Redis 并迁移；运行 `capacity` 测试；记录主机负载；把 `results.jsonl` 汇总成 `summary.md`，每个指标给出各轮的最小–最大范围 |
| `scripts/relay_upstream.py` | 本地 TLS 上游替身。同一端口提供 Responses（JSON、SSE、WebSocket）和 Messages（JSON、SSE、count_tokens），支持 HTTP/1.1 keep-alive。路径前缀 `/a/v1`、`/b/v1` 选择通道；每个通道可以通过控制端口设置首字节延迟、事件数、事件间隔、事件大小、用量和错误率（429 或 503 都使用厂商文档规定的错误信封） |
| `tests/integration/relay_load_kit.py` | Relay 进程组（每个进程使用独立的节点数据库登录）、原始 HTTP/1.1 客户端、`pg_stat_activity` 采样、进程 RSS/CPU 采样、PostgreSQL 语句耗时、账本核对 |
| `tests/integration/test_relay_load.py` | 场景。带 `integration` 和 `capacity` 标记，只有通过 `scripts/relay_load.py` 运行时才会执行 |
| `src/relay/tests/tokenizer_capacity.rs` | 本地分词估算器的离线测量（`#[ignore]`，由 `tokens` 场景调用） |

## 测量方法

**负载生成。** 客户端是同一 Python 进程中的原始 HTTP/1.1 客户端。Relay 对每个响应都关闭连接，所以每个请求都会新建 TCP 连接。稳态 profile 采用开环到达：请求按计划时间发出，不等待前一个请求完成。突发 profile 同时发出全部请求。请求按顺序轮流分配到各节点。WebSocket 使用 `websockets` 客户端。

**指标口径。**

| 指标 | 定义 |
| --- | --- |
| 输入速率 | 成功请求数 ÷（第一个请求发出 → 最后一条用量证据提交）。与 Python 基线的“实际输入请求/秒”口径相同 |
| 上游前开销 | 客户端发出请求 → 上游替身收到请求，两边都使用系统范围的 `time.monotonic`。包含 Key 鉴权、Redis 租约、`get_credential_envelope`、`reserve_request`、`start_attempt`、连接池等待和连接上游 |
| 证据提交延迟 | 上游替身写完响应（墙钟）→ 该请求最后一条用量事件提交（`pg_xact_commit_timestamp`）。包含写给客户端、等待写出回执、两次 `append_usage_event` 和连接池等待 |
| SQL 耗时 | 每个节点登录都设置了 `log_min_duration_statement=0`，从 PostgreSQL 日志解析每条 `gateway_v1.*` 在服务端的 execute 耗时。包含锁等待，不包含连接池等待和网络往返 |
| 结算 p95/p99 | 最后一条用量证据提交 → 对应 `usage_debit` 提交，与 Python 基线相同 |
| 输入结束积压、清空 | 最后一条用量证据提交时仍未结算的请求数；从该时刻到最后一个任务 `done` 的时间 |
| 锁等待、连接池 | 每 100 ms 采样一次节点登录在 `pg_stat_activity` 中的会话：`wait_event_type='Lock'` 的会话数、连接数，以及“某个节点的活跃连接数达到池上限”的采样占比（此时新的 SQL 调用必须等待连接池） |
| RSS、CPU | 每 500 ms 用 `ps` 采样一次 Relay、PostgreSQL（postmaster 及其子进程）、Redis、Worker、上游替身和客户端。CPU 以“核”为单位，等于 CPU 时间增量 ÷ 墙钟时间 |

**资金一致性。** 每个 profile 结算后都会核对：每个成功交付的请求恰好一笔 `usage_debit`，金额等于上游替身报告的用量乘以售价；没有重复扣费；不在 review 状态的请求不再持有预留；每个钱包的 `held_amount` 等于仍持有预留的请求之和；每个钱包余额等于其流水之和；每个预算期间的 `reserved` 等于其预算占用之和。进入 review 的请求会列出原因（例如 `unknown_outcome`、`missing_usage`），这也是设计中的核对路径。

**可信度。** 每个 profile 开始前，脚手架会等待其他进程的 CPU 占用降到 250%（2.5 个核）以下，最多等待 5 分钟。运行期间每 2 秒采样一次其他进程的 CPU。运行期间均值超过 250% 的 profile 会被标记为 contended，并最多重跑两次。每条记录都保存了运行前后的 `load1`、`load5`、核数，以及运行期间其他进程的 CPU 均值和峰值。下表中的范围取每轮最后一次运行的结果；如果重跑后仍然是 contended，会单独注明。

## 结果

除非另有说明，表中数值都是两轮的最小–最大范围，第二轮按相反顺序运行各 profile。标记 ⚠n 表示有 n 轮在重跑两次后仍被判为 contended，即运行期间其他进程的 CPU 均值超过 250%。各列的口径见[测量方法](#测量方法)。

Python 模拟器的每个节点只有一个连接，同一时刻只处理一个请求。突发时，它在每个节点上依次发送 8 个请求。Rust Relay 的每个节点有 8 个连接，同一时刻会把 8 个请求都送进 PostgreSQL。因此两组数据只能比较量级，不能逐格对比。

### 故障转移

4 个节点，8 家企业。主部署和备用部署是同一上游替身的 `/a` 和 `/b` 两个通道，优先级分别为 0 和 1。50 请求/秒，持续 20 秒，共 1,000 个请求。主通道按设置的比例返回 429 `rate_limit_exceeded` 或 503 `server_is_overloaded`。**只有一轮**：数据来自正式运行前的冒烟运行，使用同一个 Relay 二进制和同一套 SQL，那一版脚手架还不记录输入速率和运行期间其他进程的 CPU。运行前其他进程的 CPU 为 67–239%。正式运行在执行到这个场景之前就停止了。

### 资金一致性

全部 89 个带账本检查的 profile 记录中，共有 67,960 个请求被扣费：重复扣费、漏扣和金额错误都是 0；不在 review 状态却仍持有预留的请求为 0；钱包余额与流水、`held_amount` 与仍持有的预留、预算期间的 `reserved` 与预算占用之间，不一致都是 0；没有未完成的请求。进入 review 的请求都是预期的核对路径：

- 故障转移：每个失败尝试一个 `missing_usage`，共 2,500 个，客户只按交付的尝试扣费一次；
- WS 中途断线：64 个 `unknown_outcome`，以及 64 个 `missing_usage`；
- 慢客户端：1 个流被上游中断，`unknown_outcome` 和 `missing_usage` 各一个。

因 `settlement_backlog`、连接池超时、语句超时被拒绝的请求，要么没有预留，要么已经以 `canceled/released` 释放了预留。

## 瓶颈分析

### 1. 热点企业串行，并且节点连接数没有上限

- **机制。** `gateway_v1.reserve_request` 最终调用 `billing.v1_reserve_guarded_capacity`，先执行 `pg_advisory_xact_lock(hashtextextended(org::text,398221))`，再对钱包执行 `SELECT … FOR UPDATE`。`gateway_v1.start_attempt` 调用 `billing.v1_attempt`，先取同一把 advisory lock，再对钱包执行 `FOR SHARE`。所以同一企业的每个请求要依次通过两个串行区，每个串行区都包含一次同步提交。两把锁都在事务结束时才释放，所以快照展开和 Key 扫描（见下文）虽然在取锁之前执行，也会拉长事务。
- **证据。**
  - 64 个节点、每节点 8 个连接时，热点突发采样到 459–475 个会话处于 `wait_event_type=Lock`（`advisory`），节点连接峰值 513 个。`reserve_request` 和 `start_attempt` 在服务端的 p99 都接近 8 秒的 statement_timeout（7.5–8.0 秒）。
  - 50–52% 的采样点上，至少有一个节点的 8 个连接全部处于活跃状态。失败的请求都停在第一条 SQL（`get_credential_envelope`，连接池等待超过 5 秒）或语句超时。
  - 同一负载下，连接池从 8 降到 2，锁等待峰值从约 300 降到 127，突发全部成功，`reserve_request` 的 p99 降到 0.11–0.88 秒。
  - 延长 `deadlock_timeout` 没有效果。
- **影响范围。** 热点企业会占满一个节点的全部连接。同一节点上其他企业的请求，即使它们的企业锁没有竞争，也要等待连接池。在 64 个节点、8 个连接的均摊突发中，也有 236–385 个会话在等锁。
- **单个企业的串行吞吐。** 连接池为 2 时，热点突发的输入速率为 154–431 请求/秒（其中 90% 属于热点企业）。这就是本机上单个企业在等锁会话数受控时的大致上限。

### 2. 单个 Worker 的结算吞吐

- **证据。**
  - 每个 profile 的 Worker CPU 时间除以已结算的请求数，得到每笔 7–13 ms（最小 5.8 ms，最大 16.4 ms）。
  - 大批积压时（突发后积压约 500 笔）的清空速度为 45–143 笔/秒，Python 基线为 290–390 笔/秒。
  - 50 请求/秒的稳态下，Worker 已经用掉 0.4–0.64 个核。主机繁忙、Worker 被调度到能效核上时，它跟不上输入，积压上升到 300–970 笔。
  - 以每秒约 1,080 个请求输入时，积压在 1 秒左右达到 1,024，新的预留被拒绝。
- **未完成的验证。** `hotwallet` 场景（`--scenarios hotwallet`）用来区分两个因素：Worker 结算时用 `FOR UPDATE OF a SKIP LOCKED` 锁钱包行，会和热点企业的预留互相阻塞；backlog 触发器在企业锁内扫描最多 1,024 个 ready 任务，会拉长串行区。脚手架已经新增了按阻塞者分类的 `pg_blocking_pids` 采样，以及 Worker 事务时长采样，但这次没有运行。

### 3. 快照规模放大每个请求的 SQL 成本

- **机制。**
  - **SQL 侧。** `reserve_with_guardrail`（`reserve_request` 的最终实现）和 `start_attempt` 都调用 `publication.v1_snapshot(rev, …)->'manifest'`。这个函数每次都会解开整个 manifest，并且执行 `encode(s.payload_bytes,'base64')`，即使调用方只需要 manifest。随后，`reserve` 还要用两次 `jsonb_array_elements` 对 `key_verifiers` 做线性扫描。所以每个请求的数据库成本随集群内的 Key 数线性增长。
  - **节点侧。** 每个节点每 2–3 秒调用一次 `get_config_snapshot`（`src/relay/src/server/mod.rs` 的维护循环），每次都拉取完整应答、解码并解析，与修订是否变化无关。
- **证据。** 1 万个 Key 时，`reserve_request` 的 p50 是无 Key 时的 9 倍，`start_attempt` 的 p50 是 10 倍，每个节点 RSS 约 96 MiB，空闲出口 22 MB/s。10 万个 Key 时，单次拉取 0.84–1.56 秒，每个节点 RSS 409 MiB，空闲出口约 160 MB/s。20 请求/秒的负载全部失败，原因是 `start_attempt` 超过 1 秒、语句超时，以及刷新失败。
- **结论。** 现有的全量快照设计只适合每个集群约 1 万个 Key 以内。

### 4. 次要发现

- **配置刷新和请求共用连接池。** 连接池被锁等待占满时，`control-plane refresh failed` 会把节点标为不健康，节点随后拒绝所有企业的请求，也会延迟应用新快照。突发和 10 万 Key 的 profile 中，每次记录到 1–34 次这样的失败。
- **慢客户端可能被判为交付未知。** 见 HTTP 一节。
- **故障转移的成本核对随流量增长。** 主部署持续返回 429 或 503 时，每个请求都会产生一个 `missing_usage` 核对事项。

## 优化建议

按收益和成本从高到低排列：

1. **按上表限制节点连接池，必要时在 PostgreSQL 前加连接池代理（成本低，收益高）。** 只需要改配置和文档。注意：Relay 在 `after_connect` 中执行 `SET statement_timeout`，PgBouncer 的 transaction 模式不会保留这类会话级设置，所以要么改用角色级设置，要么使用 session 模式。
2. **准入 SQL 不再展开快照（成本中等，收益高）。** 新增一个只返回所需字段的函数，例如只返回 manifest、不做 base64 的 `v1_manifest`，并在发布时把 Key 校验数据写入按 `(cluster_id, revision, key_id)` 建索引的表。`reserve_*` 和 `start_attempt` 改为按索引查找。这样每个请求的成本与 Key 数无关。需要新迁移和发布路径的配合，不改变资金语义。
3. **快照只在修订变化时拉取，并支持 Key 增量或回查（成本中等，收益高）。** 先用轻量函数（只返回修订号、sha256 和已应用修订号）或 Redis 当前指针判断是否变化，没有变化就不拉取；`get_config_snapshot` 只返回原文。Key 有两种方式：一是从快照中拆出来，按 identity 序号增量下发；二是快照中找不到时，调用按摘要查询的 `gateway_v1` 函数回查，并对未命中做负缓存和限速。这一项需要改协议和 Relay。注意：现在的周期性全量拉取同时承担 Key 撤销和集群范围失效（`snapshot_scope_expired`）的检测，改为条件拉取时必须保留这些检测的时限。
4. **提高 Worker 吞吐，并让它水平扩展（成本中等，收益高）。** 先分析每笔 7–13 ms CPU 的构成：归一化、成本记录、报表投影等。然后验证多个 Worker 进程并发结算的正确性和吞吐，Worker 认领任务已经使用 `SKIP LOCKED`。还可以评估按账户批量结算：在一个事务里结算同一账户的多笔请求，减少对热点钱包行的加锁次数。
5. **合并 `reserve_request` 和 `start_attempt`（成本中等，收益中高）。** 预留时节点已经选好了部署，可以在同一个事务中登记第一次尝试。这样热点企业每个请求只经过一次串行区，少一次往返，也少一次同步提交。故障转移时的后续尝试仍然使用 `start_attempt`。要保持“预留成功但尝试登记失败”时的取消语义。
6. **配置刷新使用单独的连接（成本低，收益中）。** 维护循环从主连接池的连接参数单独建一个连接，避免请求的锁等待把节点刷成不健康、进而拒绝所有企业的请求。需要先决定：连接池耗尽时节点是否应该退出负载均衡。
7. **SSE 和 WS 按写出进展判定交付（成本低，涉及交付语义）。** 把等待终态写出的固定 30 秒改为“30 秒内没有写出进展才超时”，或者在 Relay 侧限制排队的字节数，让慢客户端的背压传到上游。这会改变“交付未知”的判定，需要按资金语义评审，本次没有修改。
8. **故障转移产生的核对事项合并处理（成本低到中）。** 对“厂商文档已证明没有执行”的失败尝试（Declined），可以记录为零成本，或者按部署和时段汇总，避免核对队列随流量增长。
9. **给节点预先分配额度（成本高，热点收益最高，有超支风险）。** 节点一次从钱包和预算预留一块额度（例如 50 USD），之后在本地为每个请求扣减这块额度，只有补充额度时才取企业锁。评估如下：
   - **收益。** 热点企业不再按请求串行，吞吐取决于补充频率。
   - **超支风险。** 最大超支等于所有节点未用额度之和。例如 64 个节点 × 50 USD = 3,200 USD。冻结钱包、停用 Key 或预算到期时，需要立即收回所有节点的额度；节点崩溃时，额度要到租期结束才释放。
   - **预算语义的变化。** 项目和 Key 层级的预算必须分别分配额度，否则只能在本地近似检查，这会把“预留前精确拒绝”变成“在额度范围内允许超出”。
   - **账本仍按请求结算。** Worker 要把每笔用量归到对应的额度块，并处理退还。

   这是对资金语义的实质改动，建议在第 1、2、4、5 项都完成、并且热点企业的实际流量证明仍然不够时，再单独设计和评审。

## 局限

- 只有一台共享开发机。PostgreSQL、Redis、Worker、全部 Relay、上游替身和客户端都运行在同一台机器上，测量期间还有其他会话的虚拟机和测试在运行。M5 的性能核和能效核速度不同，单线程 Worker 的速度会随调度变化。没有真实网络往返、TLS 终止层和跨地域延迟，也没有真实厂商上游。**这些数据不代表部署环境的容量。**
- 应用户要求，为了避免主机过载，本次在运行完全部场景之前就停止了：
  - 快照场景只有一轮；
  - 故障转移只有冒烟运行的一轮数据，那一版脚手架还没有记录输入速率和运行期间其他进程的 CPU；
  - 本地分词估算器和 `hotwallet`（Worker 暂停对照）没有运行。

  这些都可以用上面的命令补测，建议在专用机器或部署环境中进行。
- 有 ⚠ 标记的轮次，重跑后仍然受到主机负载影响。它们的结果偏差在一个方向上：延迟偏高、成功数偏低。
- `pg_blocking_pids` 和 Worker 事务时长这两项采样是在正式运行开始后才加入的，所以本次数据都不包含它们。

## 优化后

本节记录对准入路径的优化（第一、二阶段：上文[优化建议](#优化建议)第 1、2、3、5、6、7 项，以及[瓶颈](#瓶颈分析)第 1、3、4 节）。结算吞吐（瓶颈 2、建议 4、8）在另一个分支处理，不在本节。所有改动都不改变资金语义：每个改动点按什么规则扣费、什么时候进入核对，见各小节。

### 慢客户端的交付判定（设计说明）

**原来的问题。** 上游结束后，Relay 等终态块写出的时限固定为 30 秒，从上游结束时起算，写出有进展也不重置。上游结束时还有数据积在 Relay 的通道（最多 2 个事件）、hyper 的写缓冲和内核发送缓冲里，客户端读完这些数据之后终态块才能写出。客户端读得慢但一直在读时，30 秒到期就判为 `delivery=unknown`，请求进入 review，尽管客户端最后收到了完整的流。

**新的规则。**

- **写出进展**：该连接的 socket 被写入的字节数增加，即 `poll_write` 把数据交给了内核。
- **按进展计时**：两处改为“`NEXUS_RELAY_STREAM_IDLE_MS`（默认 30 秒）内没有任何写出进展才超时”，有进展就继续等：
  - 向客户端排队每一个事件；
  - 上游结束后等待终态块写出。
- **总上限**：为了不让一次只读几个字节的客户端无限占用节点，一次等待最多持续 10 倍空闲时间（默认 5 分钟）。
- **WebSocket**：每条消息的写出、每轮等待终态帧写出，按同样的规则判定。
- **没有采用“限制 Relay 侧排队字节数”的方案**：Relay 自己的队列本来就有界（2 个事件），慢客户端的背压已经传到上游。积压在内核发送缓冲里，缩小它会降低正常客户端的吞吐，也不改变判定。

**各种情况的判定和扣费。** “成功交付”的定义没有变：终态块写进了 socket。改动只决定 Relay 愿意为它等多久。

| 情况 | 交付判定 | 资金 |
| --- | --- | --- |
| 客户端读得慢但一直在读，终态块在 5 分钟上限内写出 | `succeeded`（原来超过 30 秒就是 `unknown`） | 按用量扣费，与快客户端相同 |
| 客户端一直在读，但 5 分钟上限到期时终态块仍未写出 | `unknown` | 预留保留，进入核对 |
| 客户端停止读取超过 30 秒（上游结束前或结束后） | 上游结束前：流中断；结束后：`unknown` | 预留保留，进入核对（与原来相同） |
| 客户端断开连接 | 写出失败，`unknown` | 同上 |
| 上游中途断开 | 不受影响 | 与原来相同 |
| 非流式（JSON）响应 | 不受影响：原来就等到写完或连接关闭 | 与原来相同 |

**保守原则。** 只有终态块确实写进 socket 的流，才会从 `unknown` 变为 `succeeded`；其余仍是 `unknown`，进入核对，不会因为这个改动多扣钱。字节写进内核并不等于客户端收到，这个限制与快客户端相同，没有扩大。
